## 1. DOMAIN MODEL OVERVIEW

### 1.1 Design Principles

1. **Local-first**: All data lives on device. Cloud sync is optional layer on top.
2. **Explicit over implicit**: No flat transactions with 20+ underscore flags.
3. **Single source of truth**: Each fact has one authoritative home. Exceptions are documented.
4. **Clear boundaries**: Finance Core, Planning, Advanced, Plugins.
5. **Testable by default**: Pure functions, no global state, no DOM dependencies.
6. **Simple by default**: Do not invent entities to solve hypothetical future problems.

### 1.2 Domain Boundaries

```
Finance Core (MVP-1)
  ├── Account
  ├── Transaction
  ├── Category
  ├── Budget
  └── Goal

Planning (MVP-2)
  ├── RecurringRule
  ├── SavingsRule
  └── Tag

Advanced (V1)
  ├── Transfer
  ├── Debtor / Debt / DebtRepayment
  ├── Creditor / Loan / LoanRepayment
  └── Investment / InvestmentTransaction

Plugins (Later)
  ├── Resale (Product, Sale, Shipment, Task, Event)
  └── Strony (Client, Product, Sale)
```

### 1.3 What Gets Dropped

- Legacy `incomeSources` / `incomeProfiles` dual model → unified approach in Advanced modules
- All transaction underscore flags (`_transfer`, `_excluded`, `_autoSave`, `_goalId`, `_sourceId`, etc.)
- Paired transfer transactions → first-class `Transfer` entity in V1
- Inline base64 labels → external storage or drop
- `isSubscription` flag → use `category` or `metadata` instead
- `activeMoneyPlace` global → proper view state
- `_vintedPrices` / `_vintedMeta` → separate module or drop

### 1.4 Money Precision Policy

- MVP-1 stores and calculates all monetary values as JavaScript `number` (IEEE 754 double precision).
- No rounding is applied at persistence, display, or calculation boundaries.
- Financial rounding (e.g., to 2 decimal places) is explicitly deferred to a future hardening stage.
- Legacy data import must normalize to this convention. Legacy negative amounts are handled by the import/migration layer by flipping sign to the new positive convention; the domain model itself does not weaken to accommodate legacy data.

## 2. CORE ENTITIES

### 2.1 User / Profile

```typescript
interface UserProfile {
  id: string;                    // UUID v4
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
  settings: {
    currency: string;            // MVP-1: 'PLN' only. Multi-currency is a future architectural consideration.
    theme: 'system' | 'light' | 'dark';
    privacyMode: boolean;
    excludeInvestmentsFromNetWorth: boolean; // Default false
  };
}
```

**Purpose**: Minimal user container. Owns all data.
**Scope**: MVP-1.

### 2.2 Account

```typescript
type AccountType = 'cash' | 'bank' | 'savings';

interface Account {
  id: string;
  userId: string;
  name: string;
  type: AccountType;
  icon: string;
  color: string;
  archived: boolean;             // Soft-delete / hide from views
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Represents a place where money resides.
**Scope**: MVP-1.
**Rules**:
- `type` determines inclusion in derived calculations.
- `archived` accounts are hidden from default views but remain queryable in historical contexts.
- No special "money place" enum. Users create accounts as needed.
- Default accounts: Konto (`bank`), Skarbonka (`savings`), Inne (`cash`).
- `investment` account type is deferred to V1+. Users who need investment tracking will receive it in the V1 Investment module. There is no coherent MVP-1 behavior for an investment account type.

### 2.3 Category

```typescript
type CategoryType = 'income' | 'expense';

interface Category {
  id: string;
  userId: string;
  name: string;
  type: CategoryType;
  icon: string;
  color: string;
  parentId: string | null;       // For subcategories (V1+)
  isSystem: boolean;             // Predefined categories
  systemRole: 'savings' | 'opening-balance' | null; // Stable semantic role for system categories only
  archived: boolean;             // Default false. See §2.10.
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Classify transactions for reporting and budgets.
**Scope**: MVP-1.
**Rules**:
- System categories are pre-seeded and cannot be deleted.
- User categories can be created/edited/archived. Archiving hides the category from selection but preserves existing transactions.
- `type` must match transaction type for budgets.
- `systemRole` is assigned only at seed time and never changes. It provides stable identity for domain rules:
  - `'savings'`: identifies the category used for goal contributions.
  - `'opening-balance'`: identifies the category used for account opening-balance transactions.
  - `null`: user-defined or system categories without a special role.
- **System categories must never be identified by display name in domain logic.** All exclusion, classification, and budget rules must use `id` or `systemRole`, never `name`.
- **MVP-1 categories are flat.** `parentId` is a reserved future field for V1+ subcategory support. MVP-1 must NOT implement, populate, validate, render, or depend on category hierarchy or subcategories. `parentId` MUST be `null` for all categories in MVP-1.

### 2.4 Transaction

```typescript
type TransactionType = 'income' | 'expense';

interface Transaction {
  id: string;
  userId: string;
  accountId: string;             // Source account
  amount: number;                // Always positive; sign determined by type
  type: TransactionType;
  categoryId: string | null;     // FK to Category
  description: string;
  date: string;                  // ISO date: YYYY-MM-DD
  notes: string;                 // Always string, empty if none
  metadata: Record<string, any>; // Optional extension point
  archived: boolean;             // Default false. See §6.3 and §13.3.
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: The fundamental financial event.
**Scope**: MVP-1.
**Rules**:
- `amount` is always positive. For expenses, the type field indicates direction.
- `accountId` is required.
- `categoryId` is required for MVP-1 (can be `null` for system transactions).
- `notes` is always `""` when empty — no `undefined`.
- `metadata` is optional and generic. No exhaustive list of keys.
- **Archived transactions** (`archived=true`) are excluded from all current financial calculations: balances, reports, Safe-to-Spend, budget progress, and income/expense statistics. They remain in the persistent record and may be included in historical queries if the caller explicitly requests them. `archived` replaces legacy `_excluded`; it has uniform scope and deterministic meaning across all calculations. See §13.3.
- **Duplicate detection** is non-blocking. It is an informational check only. It MUST never prevent transaction creation or update.
- **Opening-balance transactions** use `category.systemRole === 'opening-balance'` (or `metadata.openingBalance=true`) and are excluded from ordinary income/expense reports and Safe-to-Spend. See §6.4.
- **Goal-contribution transactions** use `category.systemRole === 'savings'` and `metadata.goalId=<goal id>`. They are excluded from ordinary expense reports and budget progress. See §2.7.
- **No `tags` field in MVP-1.** Tags are deferred to MVP-2.
- **No `type='transfer'` in MVP-1.** Transfers are represented as paired transactions in V1.

### 2.5 Transfer (V1+)

```typescript
interface Transfer {
  id: string;
  userId: string;
  fromAccountId: string;
  toAccountId: string;
  amount: number;                // Always positive
  fee: number;                   // Default 0
  description: string;
  date: string;                  // ISO date: YYYY-MM-DD
  tags: string[];
  notes: string;
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Move money between accounts with clean audit trail.
**Scope**: V1 (REDESIGN).
**Rules**:
- `Transfer` is the canonical business operation.
- Creating a Transfer generates two accounting transactions: an expense from `fromAccountId` and an income to `toAccountId`.
- Both transactions share `metadata.transferId` linking back to the parent Transfer.
- Transfer-linked transactions are **excluded from income/expense reports**.
- Transfer-linked transactions **are included in account balances** for both source and destination accounts.
- Transfer-linked transactions **must not inflate income/expense statistics**.
- `fee` is recorded as an additional expense transaction linked via `metadata.transferId`.
  - The fee reduces the `fromAccountId` balance.
  - The fee appears in expense reports under the fee's category.
  - The `toAccountId` receives only the transfer amount, not the fee.

### 2.6 Budget

```typescript
interface Budget {
  id: string;
  userId: string;
  categoryId: string;            // FK to Category
  amount: number;                // Monthly limit, > 0
  period: 'monthly';             // MVP-1 only. No other periods are supported.
  archived: boolean;             // Default false. See §2.10.
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Limit spending in a category per month.
**Scope**: MVP-1.
**Rules**:
- One budget per category per user.
- `amount` must be > 0.
- `period` is always `'monthly'` in MVP-1. No weekly, yearly, or custom periods.
- Progress is derived: sum of expenses in category for the month.
- **MVP-1 budgets are monthly-only.** No weekly or custom periods.

### 2.7 Goal

```typescript
interface Goal {
  id: string;
  userId: string;
  name: string;
  target: number;                // > 0
  current: number;               // Authoritative cache, rebuildable from transactions. See invariant in §2.7.
  currentLastRebuiltAt: string | null; // ISO datetime of last full rebuild. Null if never rebuilt.
  deadline: string | null;       // ISO date or null
  icon: string;
  color: string;
  priority: 'low' | 'medium' | 'high';
  archived: boolean;             // Default false. Excluded from Safe-to-Spend and reports.
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Savings target with progress tracking.
**Scope**: MVP-1.
**Rules**:
- **Invariant**: `current` MUST equal the sum of all non-archived transactions where `metadata.goalId === goal.id` and `category.systemRole === 'savings'`. This invariant is the single source of truth; `current` is a persisted cache of that sum.
- On any write that creates, updates, or deletes a qualifying transaction, the application MUST update `current` in the same unit of work. If the write fails or is reversed, `current` MUST be restored to the invariant value.
- `current` is an exact rebuildable cache. It MUST equal the sum of all qualifying, non-archived goal-contribution transactions. `current` MUST NOT be clamped to `target`.
- A `depositToGoal` operation MUST reject a contribution when `amount > target - current`. Such rejection uses the application's validation/business-rule failure semantics. When rejected, the contribution transaction MUST NOT be created and `current` MUST NOT change.
- `rebuildGoalCurrent` MUST always restore the exact ledger-derived sum and MUST NOT clamp it.
- No alternative source of truth for `current` exists.
- `deadline` is optional. Without it, no ETA is calculated.
- Manual deposits create a qualifying transaction and update `current` atomically.
- **MVP-1 accounting representation**: A goal contribution is a single `Transaction` with:
  - `type='expense'`
  - `categoryId` = system category with `systemRole === 'savings'`
  - `accountId` = source spendable account
  - `metadata.goalId=<goal id>`
  - `amount` = contribution amount
- This transaction reduces the source account balance via normal balance calculation.
- The transaction increments `goal.current` by the same amount as part of the invariant.
- Goal-contribution transactions are excluded from ordinary expense reports and budget progress by `category.systemRole === 'savings'` (not by display name). They do not inflate ordinary expense statistics.
- Safe-to-Spend uses `(goal.target - goal.current) / monthsLeft` for goals with deadlines and remaining > 0. Because `current` already reflects the reduced account balance, the remaining requirement is not double-counted.
- **Why this does not require the V1 Transfer entity**: A Transfer moves money between two accounts. A goal contribution moves money from an account to a tracked goal state (`goal.current`). This is a single transaction with a well-known metadata key, not a paired transfer. The V1 Transfer entity is reserved for account-to-account movements.
- **Rebuild rule**: If `current` diverges from the transaction sum (e.g., after a failed partial write, import, or correction), the application recalculates it by summing all qualifying transactions and sets `currentLastRebuiltAt` to the rebuild timestamp. Rebuild is a repair operation, not a normal write path.
- **Correction/reversal**: If a goal-contribution transaction is corrected to a different amount, the delta (`newAmount - oldAmount`) is applied to `current`. If the transaction is deleted, `current` is decremented by the deleted transaction's `amount`. If the transaction is archived, `current` is decremented by the archived transaction's `amount`.
- **Goal archival**: An archived goal is excluded from Safe-to-Spend and reports. Its `current` value is preserved. Existing goal-contribution transactions remain in the ledger and retain `metadata.goalId`. They continue to be excluded from ordinary expense reports by their category system role.

### 2.8 Recurring Rule (MVP-2)

```typescript
type Frequency = 'weekly' | 'monthly' | 'yearly';

interface RecurringRule {
  id: string;
  userId: string;
  name: string;
  type: TransactionType;         // income | expense
  amount: number;
  categoryId: string | null;
  accountId: string | null;
  description: string;
  frequency: Frequency;
  dayOfMonth: number | null;     // 1-31, null for weekly/yearly
  startDate: string;             // ISO date
  active: boolean;
  lastGenerated: string | null;  // ISO date of last generated transaction
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Generate transactions automatically.
**Scope**: MVP-2 (NEXT).
**Rules**:
- `type` is `income` or `expense`. Transfers are not generated by recurring rules in MVP-2 (V1+ feature).
- `lastGenerated` replaces `lastBooked`.
- `dayOfMonth` is clamped to month max days during generation.
- **Weekly scheduling**: `startDate` provides the deterministic weekday. Each occurrence falls on the same weekday as `startDate`.
- **Monthly scheduling**: `dayOfMonth` is used, clamped to the target month's max days. If `dayOfMonth` is null, defaults to the `startDate` day.
- **Yearly scheduling**: Uses the month and day from `startDate`. `dayOfMonth` is ignored; the occurrence falls on the same month/day as `startDate`, clamped to February 28/29 if needed.

### 2.9 Savings Rule (MVP-2)

```typescript
type SavingsTrigger = 'on_income' | 'on_expense' | 'scheduled';
type SavingsAction = 'to_goal' | 'to_account';

interface SavingsRule {
  id: string;
  userId: string;
  name: string;
  active: boolean;
  trigger: SavingsTrigger;
  sourceFilter: string | null;   // accountId for on_income/on_expense; null or accountId for scheduled
  action: SavingsAction;
  targetId: string;              // goalId or accountId
  percentage: number | null;     // 0-100, for on_income/on_expense; mutually exclusive with roundUp
  roundUp: boolean;              // for on_expense only
  schedule: {                    // for scheduled trigger
    frequency: Frequency;
    dayOfMonth: number | null;
    amount: number;
  } | null;
  createdAt: string;             // ISO datetime
  updatedAt: string;             // ISO datetime
}
```

**Purpose**: Unified auto-save mechanism.
**Scope**: MVP-2 (NEXT).
**Rules**:
- `percentage` and `roundUp` are mutually exclusive per trigger type.
- `sourceFilter` semantics:
  - `on_income`: `sourceFilter` is the `accountId` where income was received. Null means all accounts.
  - `on_expense`: `sourceFilter` is the `accountId` where expense was paid. Null means all accounts.
  - `scheduled`: `sourceFilter` is the source `accountId` for `to_account` actions. For `to_goal`, `sourceFilter` is optional (defaults to all accounts) or a specific `accountId`.
- `to_goal` updates `goal.current` directly and creates an expense transaction.
- `to_account` creates paired transactions: expense from `sourceFilter` account, income to `targetId` account.
- **Valid combinations**:
  - `on_income` + `to_goal`: `percentage` required, `roundUp` must be false/null
  - `on_income` + `to_account`: `percentage` required, `roundUp` must be false/null
  - `on_expense` + `to_goal`: `percentage` XOR `roundUp` (exactly one)
  - `on_expense` + `to_account`: `percentage` XOR `roundUp` (exactly one)
  - `scheduled` + `to_goal`: `schedule` required, `sourceFilter` optional, `percentage`/`roundUp` not used
  - `scheduled` + `to_account`: `schedule` required, `sourceFilter` MUST be a specific `accountId`, `percentage`/`roundUp` not used

### 2.10 Archive / Lifecycle Semantics

**Archived Account**:
- Excluded from all current balances, net worth, and Safe-to-Spend.
- Retains all historical transactions.
- Historical as-of queries may include archived accounts/transactions if the caller explicitly requests them.
- An account with a non-zero balance MAY be archived. The balance is not reset.
- New transactions MUST NOT reference an archived `accountId`. If a transaction references an archived account, it is excluded from current balances.

**Archived Category**:
- Hidden from selection in transaction entry and reports.
- Existing transactions retain their `categoryId`.
- An archived category is not shown in standard category breakdowns unless explicitly requested.
- **System categories cannot be archived.**

**Archived Budget**:
- Excluded from active-budget queries and budget progress calculations.
- The spending limit for that category is no longer enforced.
- Existing transactions are not affected. Historical budget progress becomes inaccessible.
- Remains in persistent record and may be included in historical queries if explicitly requested.

**Archived Goal**:
- Excluded from Safe-to-Spend and goal reports.
- `current` value is preserved.
- Existing goal-contribution transactions remain in the ledger and retain `metadata.goalId`.
- Goal-contribution transactions continue to be excluded from ordinary expense reports by their category system role.
- **A goal with non-zero `current` may be archived.**

**Archived Transaction**:
- Excluded from all current financial calculations: balances, reports, Safe-to-Spend, budget progress, and income/expense statistics.
- Persists in the record and may be included in historical queries if the caller explicitly requests them.
- Replaces legacy `_excluded` with uniform, deterministic scope across all calculations.
- Does NOT mean the transaction record is deleted.

**Ownership Invariant**:
- Every `accountId`, `categoryId`, `goalId`, `parentId`, and metadata link (`transferId`, `recurringRuleId`, `savingsRuleId`, `debtId`, `debtRepaymentId`, `loanId`, `loanRepaymentId`) MUST resolve to an entity owned by the same `userId` as the referencing transaction or entity.
- This is a domain/application invariant. It is enforced at the boundary layer (repository or service), not by database foreign keys.

**Orphan Prevention**:
- **Category**: User categories are archived (not deleted) if existing transactions reference them. This prevents orphaned `categoryId` references.
- **Goal**: Goals are archived (not deleted) if existing transactions reference them via `metadata.goalId`. This prevents orphaned goal references.
- **Account**: Accounts are archived (not deleted) if existing transactions reference them. This preserves ledger integrity.
- Destructive deletion of any entity that is referenced by persisted transactions is forbidden in MVP-1.

## 5. SOURCE OF TRUTH VS DERIVED DATA

## 6. TRANSACTION MODEL

### 6.1 Why This Model

Legacy transactions use 20+ underscore flags encoding domain-specific semantics. This makes the schema hard to evolve and creates hidden coupling between core finance and niche modules.

**Solution**: Core transaction stays clean. Domain-specific data goes in `metadata` or separate entities.

### 6.2 Transaction Types in Greenfield

| Type | Meaning | Balance Impact | Reports |
|---|---|---|---|
| `income` | Money in | +account | Included in cash-flow; excluded if `metadata.openingBalance=true` |
| `expense` | Money out | -account | Included in cash-flow; excluded if `metadata.openingBalance=true` or `category.systemRole === 'savings'` |

**MVP-1 has no transfer type.** Transfers are handled as paired transactions in V1+.

### 6.3 Metadata Usage

`metadata` is a limited extension point with three tiers:

1. **Generic optional metadata**: Any key-value pairs not covered by well-known keys. Consumers must ignore unknown keys.
2. **Well-known module relations**: Controlled keys defined below. Core domain rules must not depend on arbitrary string keys outside this set.
3. **Must NOT be in metadata**: Core domain fields that require explicit schema support: `accountId`, `amount`, `type`, `categoryId`, `date`, `description`, `notes`, `archived`, `userId`, `id`, `createdAt`, `updatedAt`.

| Key | Module | Purpose |
|---|---|---|
| `transferId` | Transfer (V1) | Links paired transfer transactions |
| `recurringRuleId` | Recurring (MVP-2) | Links to RecurringRule |
| `savingsRuleId` | SavingsRule (MVP-2) | Links to SavingsRule |
| `goalId` | Goals | Links to Goal |
| `sourceId` | Resale/Strony/Giełda | Links to external source identifier |
| `debtId` | Debtors (V1) | Links to Debt |
| `debtRepaymentId` | Debtors (V1) | Links to DebtRepayment |
| `loanId` | Creditors (V1) | Links to Loan |
| `loanRepaymentId` | Creditors (V1) | Links to LoanRepayment |
| `openingBalance` | Core | Marks initial balance transaction |

Core domain relationships must not depend on arbitrary string keys outside this controlled set.

### 6.4 Opening Balance

A newly created account can have a non-zero starting balance by creating an initial transaction. The transaction type and sign depend on the starting balance:

- **Positive opening balance**: `type='income'`, `amount = balance`, `category.systemRole = 'opening-balance'` (or `metadata.openingBalance = true`), `metadata.openingBalance = true`.
- **Zero opening balance**: No transaction is required. The account starts at `0`.
- **Negative opening balance (overdraft)**: `type='expense'`, `amount = abs(balance)`, `category.systemRole = 'opening-balance'` (or `metadata.openingBalance = true`), `metadata.openingBalance = true`. This records the overdraft as an expense against the account without violating the positive-amount rule.

**Rules**:
- Opening-balance transactions affect the account balance.
- Opening-balance transactions are **excluded from income/expense statistics** and other inappropriate cash-flow metrics.
- Opening-balance transactions are **excluded from Safe-to-Spend calculations**.
- Opening-balance transactions are included in the transaction history for the account.
- The category for an opening-balance transaction MUST be a system category with `systemRole === 'opening-balance'` or carry `metadata.openingBalance = true`.

## 7. ACCOUNT / BALANCE MODEL

### 7.1 Account Types

| Type | In Net Worth | In Safe-to-Spend | Notes |
|---|---|---|---|
| `bank` | Yes | Yes | Bank accounts |
| `cash` | Yes | Yes | Physical cash |
| `savings` | Yes | No | Piggybank, excluded from daily budget |

**Rules**:
- `savings` accounts are excluded from Safe-to-Spend but included in net worth.
- `archived` accounts are excluded from current balances, net worth, and Safe-to-Spend.
- Historical balance queries (as-of date) may include archived accounts/transactions if the caller explicitly requests them.
- `investment` account type is deferred to V1+. Users who need investment tracking will receive it in the V1 Investment module. There is no coherent MVP-1 behavior for an investment account type.

### 7.2 Balance Calculation

```typescript
function getAccountBalance(accountId: string, transactions: Transaction[]): number {
  return transactions
    .filter(t => t.accountId === accountId && !t.archived)
    .reduce((sum, t) => {
      if (t.type === 'income') return sum + t.amount;
      if (t.type === 'expense') return sum - t.amount;
      return sum;
    }, 0);
}
```

**Rules**:
- Transfers in V1+ affect both accounts via paired transactions.
- `archived` transactions are excluded.
- Negative balances are allowed (overdraft).

### 7.3 Net Worth

```typescript
function getNetWorth(accounts: Account[], balances: Map<string, number>, settings: UserProfile.settings): number {
  return accounts
    .filter(a => !a.archived && (a.type !== 'investment' || !settings.excludeInvestmentsFromNetWorth))
    .reduce((sum, a) => sum + (balances.get(a.id) || 0), 0);
}
```

**Rules**:
- Includes all non-archived accounts by default.
- Investment accounts are included by default. Users may exclude them via `settings.excludeInvestmentsFromNetWorth`.
- **`Account.type='investment'` is V1+ only. It does not exist in MVP-1. The `investment` account type, `Investment` entity, and `InvestmentTransaction` entity are all V1+ scope and must not be implemented, populated, validated, rendered, or depended on in MVP-1.** The Net Worth formula is documented here for V1+; Net Worth itself is not part of MVP-1.
- **Scope**: V1+. Not part of MVP-1.

### 7.4 Safe-to-Spend Spannable Accounts

```typescript
function getSpendableAccounts(accounts: Account[]): Account[] {
  return accounts.filter(a => !a.archived && (a.type === 'bank' || a.type === 'cash'));
}
```

**Rules**:
- Only `bank` and `cash` accounts contribute to Safe-to-Spend.
- `savings` is excluded.
- `investment` account type does not exist in MVP-1 (V1+ only).
- Legacy `konto` concept is replaced by explicit account types.

### 7.5 Safe-to-Spend Calculation (MVP-1)

```typescript
function computeSafeToSpendMVP1(inputs: {
  freeFunds: number;
  goalsReq: number;
  daysLeft: number;
}): { safeTotal: number; perDay: number } {
  const safeTotal = inputs.freeFunds - inputs.goalsReq;
  const clampedDays = Math.max(1, inputs.daysLeft);
  const perDay = safeTotal / clampedDays;
  return { safeTotal, perDay };
}
```

**Rules**:
- **MVP-1 inputs**: `freeFunds` (sum of spendable account balances), `goalsReq` (sum of required monthly goal deposits), `daysLeft` (days remaining in current month).
- **Explicit scope decision**: MVP-1 Safe-to-Spend does NOT subtract `upcomingBills`. The legacy formula was `freeFunds - bills - goalsReq`. Representing `bills` in MVP-1 without the full `RecurringRule` system would require a separate manual-bill entry mechanism or a minimal planned-expense entity. That mechanism is not part of the MVP-1 entity set. Therefore, MVP-1 Safe-to-Spend is a deliberate reduced behavior: `freeFunds - goalsReq`. This changes G0.4 scope and MUST be approved by Product Owner. It is not a silent preservation of the legacy formula.
- `goalsReq` = `sum(ceil((goal.target - goal.current) / monthsLeft))` for goals with `deadline` and `remaining > 0`.
- Safe-to-Spend does not double-count goal contributions: the account balance was already reduced by the goal-expense transaction, and `goal.current` already reflects the contribution. The formula only subtracts the remaining monthly requirement.
- Safe-to-Spend does not depend on `RecurringRule`. Any planned recurring-bill functionality is deferred to MVP-2.
- **Deterministic edge behavior**: If `daysLeft <= 0`, the function uses `Math.max(1, daysLeft)`. This prevents `Infinity` or `NaN` and guarantees a finite `perDay`. The UI may choose to surface `safeTotal` directly when `daysLeft` is abnormal, but the domain function never produces non-finite values.

## 12. OPEN ARCHITECTURAL QUESTIONS

### 12.1 Opening Balance Representation

**Question**: Should opening balances use a dedicated flag (`metadata.openingBalance`) or a separate entity?
**Recommendation**: Use `metadata.openingBalance=true` on the initial transaction. Simple and sufficient.

### 12.2 Investment Inclusion in Net Worth (V1+)

**Question**: Should investment accounts be included in net worth by default, or excluded until the user opts in?
**Recommendation**: Yes, include by default. User can opt out via `settings.excludeInvestmentsFromNetWorth`.
**Note**: `Account.type='investment'` is deferred to V1+. This question is only relevant when the Investment module is implemented.

### 12.3 Savings Rule Round-Up

**Question**: Should `SavingsRule` support `on_expense` round-up in MVP-2 or V1?
**Recommendation**: MVP-2. Round-up is a legacy feature and not complex to implement.

### 12.4 Resale Internal Wallet

**Question**: If Resale is built, should it use a dedicated `Account` with `type='savings'`?
**Recommendation**: Yes. Eliminates `_resaleBalance` flags and makes wallet balance a first-class account balance.

### 12.5 Debt/Loan Interest

**Question**: Should interest be calculated in the model?
**Recommendation**: Store `interest` as display-only info. Calculate remaining as `max(0, amount - sum(repayments))`. Add amortization schedule in V1+ if needed.

## 13. RECOMMENDED FINAL MODEL

### 13.1 Core Schema (MVP-1)

```
UserProfile
  └── settings

Account
  └── transactions

Category
  ├── transactions
  └── budgets

Transaction
  ├── account
  ├── category
  └── metadata

Budget
  └── category

Goal
  └── (rebuildable cache) current, target
```

### 13.2 Extended Schema (MVP-2)

```
RecurringRule
  └── transactions (via metadata.recurringRuleId)

SavingsRule
  └── transactions (via metadata.savingsRuleId)

Tag
  └── transactions
```

### 13.3 Advanced Schema (V1+)

```
Transfer
  ├── fromAccount
  ├── toAccount
  └── transactions (via metadata.transferId)

Debtor
  └── debts
      ├── repayments
      └── transactions (via metadata)

Creditor
  └── loans
      ├── repayments
      └── transactions (via metadata)

Investment
  └── investmentTransactions
```

### 13.4 Key Design Decisions

1. **No transaction flags**: All domain-specific data lives in `metadata` or separate entities.
2. **Transfers are first-class in V1**: Eliminates paired transaction hacks.
3. **SavingsRule replaces auto-save in MVP-2**: One mechanism, not two.
4. **Account types replace money places**: More flexible, user-defined.
5. **Archived boolean on Transaction**: Soft-delete/hide without data loss.
6. **Goal.current is rebuildable cache**: It is a persisted denormalized value, not an independent source of truth. It MUST equal the sum of qualifying transactions. Correction/deletion adjusts by delta; rebuild repairs divergence.
7. **Category identity over display name**: System roles (`savings`, `opening-balance`) provide stable classification. Domain rules must not depend on category display names.
8. **Investment removed from MVP-1**: `Account.type='investment'` is V1+ only. MVP-1 uses `cash`, `bank`, `savings`.
9. **Safe-to-Spend determinism**: `daysLeft` clamped to `>= 1`. No `Infinity` or `NaN` produced.
10. **Ownership invariant**: All foreign keys must resolve to same-`userId` entities. Enforced at boundary layer.
11. **Archive over delete**: Categories, Goals, and Accounts are archived when referenced by persisted transactions. Destructive deletion is forbidden in MVP-1.
12. **Precision policy**: MVP-1 uses JavaScript `number`. No rounding at boundaries. Legacy negative amounts handled by import layer.

### 13.5 What We Preserve from Legacy

- Safe-to-Spend formula structure (`freeFunds - goalsReq`; bills deferred to MVP-2 pending product decision)
- Goal ETA formula
- Resale balance clamp (`max(0, held - spent)`)
- 48h shipping deadline
- Non-blocking duplicate detection
- Month earn stats exclusion rules
- Anomaly detection baseline (3-month average)

## 15. ARCHITECTURAL ASSUMPTIONS G1.2 MUST RESPECT

1. **Storage-agnostic core**: Domain entities must not contain Firebase paths, listeners, or global-state coupling.
2. **Repository pattern**: All persistence goes through repositories. Domain code does not call StorageAdapter directly.
3. **Pure calculators**: Balance, Safe-to-Spend, ETA, and report calculators are pure functions with explicit inputs and outputs.
4. **ISO datetime strings**: All `createdAt`/`updatedAt` fields use ISO datetime strings. Legacy `Date.now()` numbers are not used.
5. **UUID generation**: `crypto.randomUUID()` preferred; fallback acceptable for non-critical IDs.
6. **No hidden flag system**: Domain rules must not rely on undocumented string keys in `metadata`.
7. **MVP-1 has no tags**: G1.2 must not introduce `tags` on Transaction for MVP-1.
8. **MVP-1 has no transfers**: G1.2 must not introduce `Transfer` entity or `type='transfer'` for MVP-1.
9. **Goal.current is rebuildable cache**: G1.2 must maintain the invariant `current = sum(qualifying transactions)` and must update `current` atomically with any transaction write. A repair/rebuild path must exist.
10. **Safe-to-Spend inputs are explicit**: G1.2 must not have Safe-to-Spend read globals; it receives `freeFunds`, `bills`, `goalsReq`, `daysLeft`.
11. **Investment exclusion is user preference**: G1.2 must respect `settings.excludeInvestmentsFromNetWorth`.
12. **Soft-delete via `archived`**: G1.2 must not hard-delete accounts or transactions; use `archived`.
13. **Goal contribution identity**: G1.2 must identify goal contributions by `category.systemRole === 'savings'` AND `metadata.goalId`, never by category display name.
14. **Same-user ownership invariant**: G1.2 must enforce that every `accountId`, `categoryId`, `goalId`, `parentId`, and metadata link resolves to an entity owned by the same `userId`.
15. **No orphaned financial references**: G1.2 must not allow destructive deletion of Categories, Goals, or Accounts that are referenced by persisted transactions. Archive/deactivate instead.
16. **Safe-to-Spend determinism**: G1.2 must clamp `daysLeft` to `>= 1` and must never produce `Infinity` or `NaN`.
17. **MVP-1 has no investment accounts**: G1.2 must not expose `Account.type='investment'` in MVP-1. That type is V1+ only.
18. **Precision policy**: G1.2 must apply no rounding at persistence or calculation boundaries. Monetary values are JavaScript `number`.

| TRANSFER FEE | Accounting behavior undefined | Fee is separate expense transaction linked by `metadata.transferId`, charged to `fromAccountId`, appears in expense reports. `toAccountId` receives only transfer amount | Clear, simple accounting |
| GOAL ACCOUNTING | Goal contribution semantics underspecified | Contribution is a single expense transaction with `category.systemRole === 'savings'` and `metadata.goalId`, reducing source account balance and incrementing `goal.current`. `Goal.current` is a rebuildable cache; invariant is `current = sum(qualifying transactions). Correction/deletion/de-archival of a contribution transaction adjusts `current` by the delta. Excluded from ordinary expense reports. Does not require V1 Transfer entity | Fully explicit accounting; prevents double-counting in Safe-to-Spend; ensures recoverable state |
| SAFE-TO-SPEND | Formula includes `upcomingBills` which depends on MVP-2 `RecurringRule` | MVP-1 Safe-to-Spend = `spendable balances - goalRequirements`. `upcomingBills` is intentionally deferred to MVP-2. This is an explicit product decision that changes G0.4 scope; Product Owner approval is required. The legacy `freeFunds - bills - goalsReq` formula is not silently preserved. | Safe-to-Spend is independent of RecurringRule in MVP-1; scope change is documented |
| MULTI-CURRENCY | Undecided | MVP-1 supports PLN only. Multi-currency is a future architectural consideration, not an MVP-1 dependency | Keeps MVP-1 scope minimal; avoids premature generalization |
| GOAL CURRENT | Persisted accumulator with undefined reversal semantics | `Goal.current` is rebuildable cache. Invariant: `current = sum(qualifying transactions). Correction/deletion adjusts `current` by delta. `currentLastRebuiltAt` tracks repairs. | Eliminates irreversible divergence between ledger and goal state |
| CATEGORY CLASSIFICATION | Goal contributions identified by `category='savings'` name | Goal contributions require `category.systemRole === 'savings'` (identity-based, not name-based). System categories have stable `systemRole`. | Prevents accidental misclassification and name-collision bugs |

These decisions genuinely require Product Owner approval:

1. **MVP-1 Safe-to-Spend Scope**: Product Owner must approve the deliberate reduction from legacy `freeFunds - bills - goalsReq` to `freeFunds - goalsReq` in MVP-1. Bills require `RecurringRule` (MVP-2). If approval is not granted, MVP-1 must include a minimal bills mechanism.

## 18. WHAT MUST NOT BE MIGRATED

These legacy mechanisms are explicitly excluded from the greenfield domain model:

1. Global state architecture (`window.*` for everything)
2. Flat transaction schema with underscore flags
3. Paired transfer transactions without first-class entity
4. `activeMoneyPlace` global selector
5. `incomeSources` + `incomeProfiles` dual model
6. `isSubscription` flag on recurring rules
7. Inline base64 label storage
8. `uid()` collision-prone generator (use UUID v4)
9. `RESALE_EVENTS_MAX` hard cap
10. `_stripUndefinedDeep` persistence boundary

## Summary

The revised greenfield domain model is **smaller, simpler, and explicitly scoped** than the previous draft. It resolves all 20 identified contradictions by:

- Choosing canonical models (no dual representations)
- Aligning MVP-1 strictly with G0.4 scope, with explicit Product Owner approval required for Safe-to-Spend bills reduction
- Deferring advanced features to their correct phases
- Making Goal.current a rebuildable cache with explicit invariant and repair semantics
- Using category systemRole instead of display names for classification
- Removing the dangling MVP-1 `investment` account type
- Defining deterministic archival and orphan-prevention lifecycle rules
- Removing storage and architectural concerns from the domain layer
- Keeping metadata generic and controlled

**Key metric**: MVP-1 has 5 core entities (Account, Transaction, Category, Budget, Goal) plus lifecycle fields (`archived` on Category/Budget/Goal, `currentLastRebuiltAt` on Goal, `period: 'monthly'` on Budget). Advanced features are cleanly isolated into V1+ modules.

## 19. CONTROLLED AMENDMENT (post-R4)

**Date**: 2026-09-12
**Authority**: G1.2 final hostile audit — contradiction resolution
**Change**: Remove `Goal.current` clamping to `target`. Over-target contributions are rejected at the application boundary. `rebuildGoalCurrent` restores exact ledger sum without clamping.
**Rationale**: G1.1 R4 stated clamping; G1.2 audit determined clamping contradicts the rebuildable-cache invariant and introduces a silent second source of truth. Rejection semantics preserve the target ceiling without distorting the ledger.

**Date**: 2026-09-12
**Authority**: G1.2 final hostile audit — Budget model alignment
**Change**: Add `archived: boolean` and `period: 'monthly'` to `Budget` entity. `archived` defaults to `false`; archived budgets excluded from active queries and budget progress. `period` is always `'monthly'` in MVP-1.
**Rationale**: G1.2 requires `archiveBudget` operation and `createBudget` output `period: 'monthly'`, but G1.1 frozen domain model lacked both fields. Adding them to the domain model preserves the single source of truth and eliminates the need for application-layer state workarounds.
