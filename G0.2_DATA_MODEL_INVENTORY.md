## 3. Storage Mapping

All entities except `incomeProfiles`, `dashboardLayouts`, and `resaleSettings` are loaded via `UserDataLoader.applyMapping()` from `dbData` into `window.*` globals using the `USER_DATA_MAP` table.

- **IncomeProfiles**: loaded separately via `DataLayer.readOnce('incomeProfiles')` and assigned directly to `window.incomeProfiles`.
- **DashboardLayouts**: loaded from `data.settings.layouts` or legacy `finapp_dashboard_layouts` into `DashboardLayoutsState`; exposed as read-only `window.dashboardLayouts`.
- **ResaleSettings**: merged from `dbData['finapp_resale_settings']` with `RESALE_SETTINGS_DEFAULTS`.
- **VintedPrices/Meta**: loaded from `dbData['finapp_vinted_prices']` and `dbData['finapp_vinted_meta']`.

Firebase paths follow the pattern `users/{uid}/<SK key>` for root-level arrays. Dashboard layouts use `users/{uid}/settings/layouts/<tab>`.

## 4. Entity Relationships

- **Transactions** are the central ledger. They reference:
  - `incomeSources` via `_sourceId`
  - `goals` via `_goalId`
  - `recurringTx` via `_recurringId`
  - `stronyProducts` via `_stronyProductId`
  - `stronyClients` via `_stronyClientId`
  - `debts` (in `debtors`) via `_debtId` and `_debtRepay`
  - `loans` (in `creditors`) via `_loanId` and `_loanRepay`
- **Debtors** contain an embedded `debts` array with optional `repayments` sub-array.
- **Creditors** contain an embedded `loans` array with optional `repayments` sub-array.
- **AutoSaveRules** reference `incomeSources` via `sourceId` and `goals` via `dest` (`'goal:<id>'` format).
- **ResaleSales** reference `resaleProducts` via `productId` and `resaleShipments` via `shipmentId`.
- **ResaleTasks** optionally reference `resaleProducts` via `productId`.
- **ResaleShipments** contain `items` that reference `resaleProducts` via `productId`.
- **ResaleEvents** reference any resale entity via `entity`/`entityId`.
- **IncomeProfiles** are a separate top-level object map (not in USER_DATA_MAP). They are not directly referenced by other entities via foreign keys, but are conceptually linked to `incomeSources` by `_profileType`.

## 7. Income Model Analysis

### 7.1 IncomeSources vs IncomeProfiles

The application maintains **two parallel income models**:

- **`incomeSources`** (`finapp_income_sources`): Simple array of `{id, name, icon, _profileType?}`. Used by the source-selector bar and many legacy functions. The `_profileType` field is auto-seeded for three system sources: `'strony'`, `'resale'`, `'gielda'`. User-created sources do NOT have `_profileType`.

- **`incomeProfiles`** (`incomeProfiles`): Object map (not array) of `{id, name, icon, balance, modules, activeModules}`. Auto-seeded with three default profiles: `strony`, `resale`, `gielda`. Stored under a separate Firebase path (`users/{uid}/incomeProfiles/`), NOT under the root `dbData` node. NOT loaded by `UserDataLoader`.

### 7.2 Relationship

- `incomeSources` with `_profileType` are conceptually aligned with `incomeProfiles` keys.
- `transactions._sourceId` references `incomeSources.id`, NOT `incomeProfiles.id`.
- `IncomeProfileBalanceCalculator` treats profile `id === 'gielda'` specially, delegating to `GieldaBalanceService`.
- `SourceNetCalculator` / `SourceMonthlyEarningsCalculator` operate on `incomeSources`, not `incomeProfiles`.

### 7.3 Suspicious / Uncertain

- The dual model (`incomeSources` + `incomeProfiles`) creates potential inconsistency. There is no enforced 1:1 mapping between them.
- `incomeProfiles` has no SK key and is not in `USER_DATA_MAP`; it is loaded independently and lives outside the standard data loading lifecycle.
- The `balance` field on `IncomeProfile` is a **derived/persisted hybrid**: it is initialized to a default value (e.g., 30.00, 4333.00, 5724.00) but can be overridden by the user or updated by `applyAutoSaveRules`. There is no clear migration path if it drifts from actual transaction net.

## 8. Resale Data Model

### 8.1 Products
- `resaleProducts`: Core product catalog.
- Fields: `id`, `name`, `buyPrice`, `sellPrice`, `weight`, `link`, `links`, `notes`, `imageUrl`, `season`, `createdAt`, `priceHistory`, `minStockAlert`.
- `quantity` is **not** a core persisted field; it is dynamically added when auto-created from a resale expense (`_autoCreated: true`).
- `priceHistory` tracks buy price changes (Phase 0.1).

### 8.2 Sales
- `resaleSales`: Listing and sale records.
- Fields: `id`, `productId`, `shipmentId`, `price`, `date`, `status`, `platform`, `createdAt`, `listedAt`, `statusHistory`, `actualBuyCost`, `actualShippingCost`, `actualTotalCost`, `suggestedPrice`, `soldAt`, `shippedAt`, `returnedAt`.
- `_labelData` / `_labelName` / `_labelType` store inline shipping labels as base64 data URLs.

### 8.3 Shipments
- `resaleShipments`: Package groupings for shipping.
- Fields: `id`, `name`, `items` (`{productId, qty, sellPrice}`), `createdAt`, `ordered`, `orderedAt`, `finalPurchasePrice`, `finalShippingCost`, `finalPackageWeight`, `finalPurchaseBreakdown`.
- Actual costs are filled post-delivery via `saveShipmentActualCosts()`.

### 8.4 Tasks
- `resaleTasks`: Todo items linked to products.
- Fields: `id`, `title`, `type`, `dueDate`, `productId`, `done`, `createdAt`.

### 8.5 Events
- `resaleEvents`: Audit log of resale actions.
- Fields: `id`, `at`, `type`, `entity`, `entityId`, `meta`.
- Max 5000 events; oldest pruned.

### 8.6 Settings
- `resaleSettings`: Global defaults merged from `RESALE_SETTINGS_DEFAULTS`.
- Fields: `staleThresholdDays`, `defaultMinStockAlert`, `shipPerKg`, `platformCommissions`.

### 8.7 Resale Balance
- The internal Resale wallet is **not** a separate entity. It is computed from `transactions` flagged with:
  - `_resaleBalance` (income held in wallet)
  - `_resaleWithdraw` (withdrawal from wallet to real account)
  - `_resalePaidFromBalance` (expense paid directly from wallet)
- `ResaleBalanceCalculator` filters by `_sourceId` (income source) plus the above flags.

## 9. Transaction Data Model

### 9.1 Core Fields
- `id`, `amount`, `type`, `category`, `place`, `desc`, `date`, `createdAt`
- `tags`: string array (undefined when empty)
- `note`: string (undefined when empty)

### 9.2 System Flags (underscore-prefixed)
Transactions use a flat schema with optional underscore-prefixed fields to encode domain-specific semantics:

| Flag | Meaning | Set When |
|---|---|---|
| `_sourceId` | Links to `incomeSources.id` | Resale/Strony/Gielda income/expense |
| `_excluded` | Excluded from balance calculations | Resale internal entries, zero-place entries |
| `_transfer` | Transfer between accounts | (rarely set explicitly) |
| `_autoSave` | Auto-savings transaction | `applyAutoSaveRules` or goal round-up |
| `_goalId` | Links to `goals.id` | Goal auto-round-up expense |
| `_stronyProductId` | Links to `stronyProducts.id` | Strony product sale income |
| `_stronyClientId` | Links to `stronyClients.id` | Strony client sale income |
| `_resaleBalance` | Income held in Resale wallet | Resale income entry |
| `_resaleWithdraw` | Withdrawal from Resale wallet | Resale withdrawal expense |
| `_resaleWithdrawIncome` | Income from Resale withdrawal to real account | Resale withdrawal to real place |
| `_resalePaidFromBalance` | Expense paid from Resale balance | Resale expense from internal wallet |
| `_resaleExpType` | `'purchase'\|'shipping'\|'other'` | Resale expense categorization |
| `_resaleProducts` | Product usage snapshot | Resale purchase expense |
| `_recurringId` | Links to `recurringTx.id` | Auto-booked recurring transaction |
| `_debtId` | Links to `debtors.debts[].id` | Debt creation expense |
| `_debtRepay` | Links to `debtors.debts[].repayments[].id` | Debt repayment income |

## 10. Goals / Auto-Save Model

### 10.1 Goals
- Simple array: `{id, name, target, current, deadline, icon, color, autoSave?}`.
- `autoSave` flag enables round-up auto-saving on expenses.

### 10.2 Auto-Save Rules
- `{id, sourceId|null, pct, dest, label, active}`.
- `dest` can be a money place or `'goal:<id>'`.
- Applied on income via `applyAutoSaveRules()`.
- Creates an expense transaction with `_autoSave: true`, `category: 'savings'`, `place: 'skarbonka'`.
- If `dest` starts with `'goal:'`, also increments `goal.current`.

### 10.3 Goal Auto-Round-Save
- Separate mechanism from `autoSaveRules`.
- Triggered on every expense via `applyGoalAutoRoundSave()`.
- Rounds up the expense amount and transfers the difference to linked goals.
- Creates an internal transfer transaction with `_autoSave: true`, `_goalId: <id>`.

## 13. Uncertainties

1. **`incomeProfiles` lifecycle**: It is auto-seeded and loaded outside `UserDataLoader`, but there is no clear de-duplication or migration logic if a user manually deletes a default profile and then the app re-seeds it on next login. The `ensureIncomeProfilesExist()` function merges missing keys but does not handle renamed or user-modified profiles.

2. **`transactions.tags` persistence**: When empty, `tags` is set to `undefined` (not stripped by `_stripUndefinedDeep` because `[]` is falsy? Actually the code checks `tags.length ? tags : undefined`). This means some transactions may lack the `tags` key entirely, while others have `tags: []`. Downstream code must handle both.

3. **`transactions.note` persistence**: Same pattern as `tags`: empty string becomes `undefined`.

4. **`resaleProducts.quantity`**: Dynamically added only when auto-created from a resale expense. Manually created products never have `quantity`. This inconsistency may break quantity-based aggregations.

5. **`incomeSources._profileType`**: Only auto-seeded for the three system sources. User-created sources lack this field. Code that filters by `_profileType` must handle `undefined`.

6. **`DashboardLayoutsState` authoritative flag**: The `isAuthoritative()` mechanism and its interaction with live Firebase listeners is complex. It is unclear whether layout changes made in one tab are immediately reflected in other tabs without a reload.

7. **`_vintedPrices` / `_vintedMeta`**: These are loaded from `dbData` in `applyMapping()` but are not in `USER_DATA_MAP`. They are excluded from `save()` operations in `clearLocalState()`. It is unclear if they are ever persisted back to Firebase.

8. **Loan `dest` field**: When `dest` is set, a loan creates an income transaction. If the destination is a money place, it increases that place's balance. However, the `dest` field on the loan is not updated if the money place is later deleted or renamed.

9. **Debt `source` field**: Similar to loan `dest`, it creates an expense transaction. The `source` field on the debt is not validated against the current set of money places.

10. **`activeMoneyPlace` migration**: On first load, if `activeMoneyPlace === 'gielda'`, it is silently reset to `'konto'`. This is a one-time migration but could surprise users who previously had `'gielda'` selected.

## 14. Discovery Gaps

- **Tests/Fixtures**: No test fixtures were found in the repository. All behavioral understanding is derived from inline script analysis.
- **Firebase Schema Validation**: No schema validation layer was found. Data integrity relies on application code only.
- **Migration History**: The `src/schema/` modules exist but no migration scripts were found. It is unclear how historical data changes are tracked.
- **`_stripUndefinedDeep` behavior**: The function recursively strips `undefined` but preserves `null` and empty strings. The persistence boundary between `undefined` and empty string is not consistently applied across all entity creation sites.
- **`uid()` collision risk**: The generator uses `Date.now().toString(36)` + random suffix. Under high concurrency, collisions are unlikely but possible.
- **`RESALE_EVENTS_MAX`**: The 5000-event cap is hardcoded. No policy for archiving or exporting old events was found.
