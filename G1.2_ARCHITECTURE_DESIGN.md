## 1. ARCHITECTURE OVERVIEW

### 1.1 Design Context

G1.2 is the greenfield architecture design. It builds on G1.1 Domain Model Design and the Stage 1.x vertical slices already implemented. The architecture is a **layered, dependency-inverted** design adapted to browser + Node.js.

### 1.2 Core Principles

1. **Dependency Inversion**: Inner layers (domain) know nothing about outer layers (UI, persistence).
2. **Pure Domain**: All calculators are pure functions with no side effects, no globals, no DOM, no Firebase.
3. **Thin Adapters**: Application services read globals and delegate to domain. Storage adapters implement a contract.
4. **Browser-First**: Every module works in `<script>` tags and `node:` tests without a bundler.
5. **No Global Business Logic**: Global arrays are the data source, not the business logic owner.
6. **Incremental Extractability**: Each calculator can be extracted independently.

## 2. LAYER ARCHITECTURE

```
┌─────────────────────────────────────────────────────────────┐
│                    UI Layer (index.html)                     │
│          Script tags, event handlers, render functions       │
└────────────────────────────┬────────────────────────────────┘
                             │ calls
                             ▼
┌─────────────────────────────────────────────────────────────┐
│              Application State Layer                         │
│          src/state/application-state.js                     │
│          src/state/dashboard-layouts-state.js               │
│  Owns: UI state, session state, dashboard layouts           │
│  Knows: Nothing about Firebase, domain, or persistence      │
└────────────────────────────┬────────────────────────────────┘
                             │ reads
                             ▼
┌─────────────────────────────────────────────────────────────┐
│              Application Services Layer                      │
│          src/application/**/*-service.js                    │
│  Owns: Orchestration between globals and domain calculators │
│  Knows: Global array names, calculator locations            │
└────────────────────────────┬────────────────────────────────┘
                             │ calls
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                    Domain Layer                             │
│          src/domain/**/*-calculator.js                      │
│  Owns: Pure financial calculation functions                 │
│  Knows: Nothing except its own input/output                 │
└─────────────────────────────────────────────────────────────┘

Persistence path:
  UI / Services
    → Repository Layer
      → StorageAdapter
        → FirebaseStorageAdapter
          → Firebase Realtime Database

Cross-cutting:
  Schema Migration → operates on data before persistence
```

### 2.1 Layer Responsibilities

| Layer | Owns | Knows About | Can Do | Can Not Do |
|-------|------|-------------|--------|-----------|
| **UI** | DOM events, rendering | State getters, Service methods | Trigger actions, render state | Read globals directly, call DataLayer |
| **Application State** | UI/session state | Nothing about Firebase | Get/set state, emit changes | Access domain calculations, call persistence |
| **Application Services** | Orchestration | Global array names, calculator locations | Read globals, call calculators, return results | Manipulate DOM, call Firebase directly |
| **Domain** | Pure calculations | Nothing external | Compute from explicit inputs | Read globals, access DOM, access persistence |
| **Repository** | Domain entity CRUD | State shape, StorageAdapter | Load, save, remove entities | Read global arrays directly, access Firebase |
| **StorageAdapter** | Persistence operations | Firebase SDK | Read/write/listen | Access domain, UI, or application logic |
| **Schema Migration** | Data shape transformations | Schema versions | Validate, transform, migrate | Access Firebase, DOM, or domain logic |

## 4. TECH STACK

### 4.1 Runtime

| Component | Technology | Rationale |
|-----------|-----------|-----------|
| **UI** | Vanilla JS + HTML | No framework dependency; single-file SPA |
| **Module Pattern** | CommonJS (`module.exports` / `window.*`) | Works in Node.js tests and browser without bundler |
| **Test Runner** | Node.js built-in `node:test` | Zero-dependency, available in Node 18+ |
| **Assertions** | `node:assert/strict` | Zero-dependency |
| **Persistence (local)** | IndexedDB via `idb` library | Local-first, offline-capable |
| **Persistence (sync)** | Firebase Realtime Database | Existing sync layer (optional in greenfield) |
| **Data Validation** | Custom validators | Lightweight, no external deps |
| **Build/Bundle** | None required | Scripts load directly; rollup/vite optional for deployment |

### 4.2 Node.js Dependencies (target)

```
dependencies:
  idb: ^8.0.0          # IndexedDB wrapper
  uuid: ^9.0.0         # UUID generation (already installed)

devDependencies:
  (none — use node:test, node:assert)
```

### 4.3 Browser APIs Used

- `IndexedDB` — primary local storage
- `BroadcastChannel` / `storage` event — multi-tab sync
- `crypto.randomUUID()` — UUID generation (fallback to uuid lib)

## 5. CODING CONVENTIONS

### 5.1 Module Pattern

Every module exports a named object with named functions:

```javascript
function compute(inputs) { /* pure */ }
function computeForCurrentState() { /* bridge */ }

if (typeof module !== 'undefined' && module.exports) {
  module.exports = { compute, computeForCurrentState };
}

if (typeof window !== 'undefined') {
  window.SafeToSpendCalculator = { compute };
  window.SafeToSpendService = { computeForCurrentState };
}
```

### 5.2 Naming

| Artifact | Pattern | Example |
|----------|---------|---------|
| Calculator | `<DomainThing>Calculator` | `SafeToSpendCalculator` |
| Service | `<DomainThing>Service` | `SafeToSpendService` |
| Repository | `<Entity>Repository` | `TransactionRepository` |
| Adapter | `<Backend>StorageAdapter` | `IndexedDBStorageAdapter` |
| File path | `src/domain/<domain>/<thing>-calculator.js` | `src/domain/safe-to-spend/safe-to-spend-calculator.js` |

### 5.3 Pure Calculator Contract

```javascript
/**
 * <DomainThing>Calculator
 *
 * Pure calculation for <what it computes>.
 *
 * Operates ONLY on explicit input data.
 * Does not read globals, DOM, Firebase, or any external state.
 */
function compute(inputs) {
  // inputs must be explicit, defaults applied inside
  const x = inputs.x || 0;
  // ... pure math
  return { /* deterministic output */ };
}
```

### 5.4 Application Service Contract

```javascript
/**
 * <DomainThing>Service
 *
 * Bridge between legacy global application state and the pure domain calculator.
 *
 * Reads the current in-memory financial arrays and delegates
 * the final calculation to the domain layer.
 *
 * Does NOT:
 * - manipulate the DOM
 * - render UI
 * - call Firebase directly
 * - persist data
 * - show toasts
 */
function computeForCurrentState() {
  // Read globals
  // Call calculator
  // Return result
}
```

### 5.5 Repository Contract

```javascript
/**
 * <Entity>Repository
 *
 * CRUD operations for <Entity>.
 *
 * Knows about StorageAdapter, but NOT about:
 * - Firebase
 * - DOM
 * - Domain calculators
 */
function loadAll() { /* via StorageAdapter */ }
function save(entity) { /* via StorageAdapter */ }
function remove(id) { /* via StorageAdapter */ }
function findById(id) { /* via StorageAdapter */ }
```

### 5.6 Storage Adapter Contract

```javascript
// Required interface (already defined in src/storage/storage-adapter.js):
{
  get(key)
  set(key, value)
  update(key, updater)
  updateMany(updates)
  remove(key)
  listen(path, callback, errCallback?)  // returns unsubscribe
  listenRoot(callback, errCallback?)     // returns unsubscribe
}
```

## 6. DATA FLOW PATTERNS

### 6.1 Read Path (Calculation)

```
index.html → global array
           → ApplicationService.computeForCurrentState()
           → DomainCalculator.compute(inputs)
           → result → UI render function
```

**Rule**: Services read globals. Calculators receive explicit inputs. UI reads services.

### 6.2 Write Path (Mutation)

```
UI event handler
  → ApplicationService.mutateSomething(inputs)
    → Repository.save(entity)
      → StorageAdapter.set(key, value)
        → IndexedDBStorageAdapter / FirebaseStorageAdapter
```

**Rule**: Services orchestrate mutations. Repositories handle persistence. Services never call StorageAdapter directly.

### 6.3 Listener Path (Reactive Updates)

```
Firebase/IndexedDB change
  → StorageAdapter.listen callback
    → Repository.updateLocalCache(data)
      → ApplicationState.emit('dataChanged')
        → UI render functions
```

### 6.4 Migration Path

```
Data read from storage
  → SchemaValidator.validate(data)
    → Migrator.migrate(data, fromVersion, toVersion)
      → MigrationRegistry.apply(data, path)
        → Validated + transformed data
          → In-memory state
```

## 12. KEY DECISIONS

1. **No TypeScript**: Stay with JSDoc-annotated JavaScript for now. TypeScript is a future option.
2. **No bundler**: Scripts load directly. Use rollup/vite only for deployment packaging.
3. **No framework**: Vanilla JS + custom components. Keeps bundle small and dependencies zero.
4. **Local-first**: IndexedDB is primary storage. Firebase is sync layer (opt-in).
5. **Incremental extraction**: Each calculator is extracted independently; no big-bang rewrite.
6. **Test-first**: Characterization tests before extraction. Unit tests for every calculator.
7. **Dual module pattern**: `module.exports` + `window.*` for seamless browser/test compatibility.
8. **No global business logic**: Global arrays are data sources only. All logic in calculators/services.
9. **Derived data never persisted**: Balances, stats, reports computed on demand.
10. **Metadata extension point**: `metadata: Record<string, any>` on Transaction for future flags.

## Summary

The greenfield architecture is a **layered, dependency-inverted system** with:
- **Pure domain calculators** (no side effects, no external knowledge)
- **Thin application services** (bridge globals to domain)
- **Repositories** (domain entity CRUD)
- **Storage adapters** (pluggable persistence)
- **Schema migrations** (safe data evolution)
- **Node.js built-in test runner** (zero-dependency testing)

The existing Stage 1.x implementation already validates this architecture with 222 passing tests. The next step is to extend it by creating repositories for the remaining domain entities and wiring them to the UI.

**Key metric**: Greenfield has ~50 modules across domain, application, repositories, and infrastructure. Each module is independently testable and replaceable.
