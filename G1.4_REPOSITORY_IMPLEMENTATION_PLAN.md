## 3. REPOSITORY DESIGN PATTERN

### 3.1 Base Pattern

```javascript
/**
 * Stage 1.4+ — <Entity>Repository
 *
 * CRUD operations for <Entity>.
 *
 * Reads/writes via StorageAdapter. Maintains local cache.
 * Does NOT access Firebase, DOM, or global arrays directly.
 */
class <Entity>Repository {
  constructor(storageAdapter, userId) {
    this.storageAdapter = storageAdapter;
    this.userId = userId;
    this.entities = new Map();  // local cache
    this.listeners = new Set();
  }

  // --- CRUD ---

  async loadAll() {
    const data = await this.storageAdapter.get(this.storageKey);
    this.entities = new Map(
      (Array.isArray(data) ? data : []).map(e => [e.id, e])
    );
    return Array.from(this.entities.values());
  }

  async save(entity) {
    const validated = this.validate(entity);
    const existing = this.entities.get(validated.id);
    const toSave = existing ? { ...existing, ...validated, updatedAt: now() } : validated;
    this.entities.set(toSave.id, toSave);
    await this.storageAdapter.set(this.storageKey, Array.from(this.entities.values()));
    return toSave;
  }

  async remove(id) {
    this.entities.delete(id);
    await this.storageAdapter.set(this.storageKey, Array.from(this.entities.values()));
  }

  findById(id) {
    return this.entities.get(id) || null;
  }

  // --- Reactive ---

  listen(callback) {
    const unsub = this.storageAdapter.listen(this.storageKey, (data) => {
      this.entities = new Map(
        (Array.isArray(data) ? data : []).map(e => [e.id, e])
      );
      callback(Array.from(this.entities.values()));
    });
    this.listeners.add(unsub);
    return { unsubscribe: () => this.listeners.forEach(u => u()) };
  }
}
```

### 3.2 Validation Pattern

```javascript
validate(input) {
  const errors = [];
  if (!input.id) errors.push('id is required');
  if (!input.name || typeof input.name !== 'string') errors.push('name must be a non-empty string');
  if (errors.length > 0) throw new Error(`Validation failed: ${errors.join(', ')}`);
  return input;
}
```

### 3.3 Integration with Existing DataLayer

Repositories will initially coexist with DataLayer:
1. DataLayer continues to serve `index.html` inline scripts.
2. Repositories are used by new Application Services.
3. Over time, inline scripts migrate to use Repositories.
4. DataLayer is eventually deprecated.

**Key constraint**: Repositories and DataLayer must not write to the same key simultaneously without coordination. During migration, writes go through DataLayer; reads can come from either.

## 6. MIGRATION STRATEGY

### 6.1 Data Migration

During migration from legacy to greenfield:

```javascript
// src/schema/migrations/v1-to-v2.js
function migrateTransactionsV1toV2(data) {
  return data.map(tx => ({
    ...tx,
    metadata: {
      transferId: tx._transfer ? tx._transferId : null,
      excluded: tx._excluded || false,
      autoSave: tx._autoSave || false,
      goalId: tx._goalId || null,
      sourceId: tx._sourceId || null,
      resaleBalance: tx._resaleBalance || false
    },
    tags: tx.tags || [],
    notes: tx.notes || ''
  }));
}
```

### 6.2 Runtime Migration (Phase-in)

Repositories operate in parallel with DataLayer during migration:

```javascript
// Composition root
const txRepo = new TransactionRepository(storageAdapter, userId);
const legacyDataLayer = window.DataLayer;

// New code uses repository
const txRepo.loadAll().then(transactions => { /* ... */ });

// Legacy code continues to use DataLayer
legacyDataLayer.save(SK.transactions, newTx);
```

### 6.3 Cache Synchronization

During parallel operation, repositories and DataLayer share the same storage key. To prevent conflicts:
- Repositories use `StorageAdapter.update()` for single-entity updates (atomic).
- DataLayer uses `StorageAdapter.set()` for bulk writes.
- `updateMany()` is reserved for atomic multi-key updates (e.g., transfer: update two accounts).

### 6.4 Gradual Cutover

1. **Week 1**: Implement repositories, test in isolation.
2. **Week 2**: Wire repositories to one ApplicationService (e.g., TransactionService).
3. **Week 3**: Migrate one UI module to use repository (e.g., transaction list).
4. **Week 4**: Migrate remaining UI modules incrementally.
5. **Week 5**: Deprecate DataLayer, remove global `window.dbData` dependency.

## 7. TESTING STRATEGY

### 7.1 Unit Tests (per repository)

```javascript
const { describe, it, beforeEach } = require('node:test');
const assert = require('node:assert/strict');
const { TransactionRepository } = require('../src/repositories/transaction-repository.js');
const { MockStorageAdapter } = require('../src/storage/mock-storage-adapter.js');

describe('TransactionRepository', () => {
  let mock;
  let repo;

  beforeEach(() => {
    mock = new MockStorageAdapter('user-123');
    repo = new TransactionRepository(mock, 'user-123');
  });

  describe('save()', () => {
    it('persists entity with id', async () => {
      const tx = { id: 'tx-1', accountId: 'acc-1', amount: 100, type: 'income', date: '2026-09-01', tags: [], notes: '', metadata: {} };
      await repo.save(tx);
      const found = repo.findById('tx-1');
      assert.strictEqual(found.id, 'tx-1');
    });

    it('throws on missing id', async () => {
      await assert.rejects(() => repo.save({ amount: 100 }), /id is required/);
    });
  });

  describe('remove()', () => {
    it('removes entity', async () => {
      await repo.save({ id: 'tx-1', amount: 100, type: 'income', date: '2026-09-01', tags: [], notes: '', metadata: {} });
      await repo.remove('tx-1');
      assert.strictEqual(repo.findById('tx-1'), null);
    });
  });

  describe('listen()', () => {
    it('receives updates from storage', async () => {
      const updates = [];
      const { unsubscribe } = repo.listen(entities => updates.push(entities));
      await repo.save({ id: 'tx-1', amount: 100, type: 'income', date: '2026-09-01', tags: [], notes: '', metadata: {} });
      assert.strictEqual(updates.length, 1);
      assert.strictEqual(updates[0].length, 1);
      unsubscribe();
    });
  });
});
```

## 9. RISKS & MITIGATIONS

### 9.1 Risk: Duplicate Writes

**Problem**: DataLayer and Repository both write to same key during parallel operation.

**Mitigation**: Use `StorageAdapter.update()` for single-entity changes. Reserve `set()` for bulk initialization only.

### 9.2 Risk: Cache Staleness

**Problem**: Repository cache may diverge from Firebase if both DataLayer and Repository write.

**Mitigation**: Repositories listen to their own storage path. DataLayer writes trigger repository listener → cache updates.

### 9.3 Risk: Legacy Inline Scripts Break

**Problem**: `index.html` inline scripts depend on `window.transactions`, `window.goals`, etc.

**Mitigation**: Repositories do NOT modify global arrays. A separate bridge service (ApplicationService) copies data from repository to globals when needed. This allows gradual migration.

### 9.4 Risk: New Storage Keys Break Sync

**Problem**: New keys (`finapp_accounts`, `finapp_categories`, etc.) don't exist in existing Firebase.

**Mitigation**: Repositories seed defaults when key is empty. Migration script populates new keys from legacy data on first load.
