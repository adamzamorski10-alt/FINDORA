## 1. PURPOSE

G1.7 defines the plan for migrating the legacy `index.html` SPA to the greenfield architecture. It covers:
- Component architecture
- Render function patterns
- Event handler patterns
- Step-by-step UI migration
- Backward compatibility strategy

---

## 2. CURRENT UI LANDSCAPE

### 2.1 Architecture

`index.html` is a single-file SPA (~21,000 lines):
- Inline `<script>` tags at bottom of file
- Global functions for rendering, event handling, business logic
- Direct manipulation of `window.*` global arrays
- `renderAll()` orchestrates all renders
- Modal system via `openXModal()` / `closeXModal()`

### 2.2 Key Problems

1. **No component boundaries**: render functions are monolithic (e.g., `renderTransactions()` renders list + form + pagination).
2. **Tight coupling**: render functions read/write globals directly.
3. **No state management**: UI state (active tab, form values) scattered across functions.
4. **Hard to test**: DOM-dependent, no clear contracts.
5. **No incremental migration path**: changes to one function risk breaking others.

### 3.2 Component Contract

```javascript
/**
 * Renders a transaction list item.
 *
 * @param {Object} props
 * @param {Transaction} props.transaction
 * @param {Function} props.onEdit - (id) => void
 * @param {Function} props.onDelete - (id) => void
 * @returns {string} HTML string
 */
function TransactionListItem({ transaction, onEdit, onDelete }) {
  return `
    <div class="transaction-item" data-id="${transaction.id}">
      <span class="amount">${formatMoney(transaction.amount)}</span>
      <span class="desc">${escapeHtml(transaction.description)}</span>
      <button data-action="edit" data-id="${transaction.id}">Edit</button>
      <button data-action="delete" data-id="${transaction.id}">Delete</button>
    </div>
  `;
}
```

**Rules**:
- Components are **pure functions**: given same props, return same HTML.
- Components must NOT:
  - Read globals directly
  - Access DOM
  - Call services
  - Register event listeners
- Components return **HTML strings** (no virtual DOM, no framework).
- Event binding happens **after** render via delegation.

### 3.3 Render Pattern

```javascript
// View-level render function
function renderTransactions() {
  const container = document.getElementById('transactions-container');
  if (!container) return;

  // 1. Fetch data via service
  const transactions = window.TransactionService.getAll();
  // In async version: const transactions = await window.TransactionService.getAll();

  // 2. Render using components
  const itemsHtml = transactions.map(tx =>
    TransactionListItem({
      transaction: tx,
      onEdit: (id) => window.openTransactionModal(id),
      onDelete: (id) => window.confirmDeleteTransaction(id)
    })
  ).join('');

  container.innerHTML = `
    <div class="transaction-list">
      ${itemsHtml}
    </div>
  `;
}
```

## 5. EVENT HANDLER PATTERN

### 5.1 Delegation Pattern

Instead of inline `onclick`, use event delegation:

```javascript
// Global delegation (existing pattern, improved)
document.addEventListener('click', (e) => {
  const button = e.target.closest('button[data-action]');
  if (!button) return;

  const action = button.dataset.action;
  const id = button.dataset.id;

  switch (action) {
    case 'edit-transaction':
      window.openTransactionModal(id);
      break;
    case 'delete-transaction':
      window.confirmDeleteTransaction(id);
      break;
    case 'book-recurring':
      window.bookRecurring(id);
      break;
    // ... more actions
  }
});
```

**Rules**:
- All buttons use `data-action` and `data-id` attributes.
- Single global listener handles all clicks (performance).
- Handlers delegate to `window.*` functions (backward compatibility).

### 5.2 Service-Based Handlers

```javascript
// New pattern: handlers call services
window.onTransactionSubmit = async function(formData) {
  try {
    const service = window.TransactionService;
    if (formData.id) {
      await service.update(formData.id, formData);
    } else {
      await service.add(formData);
    }
    closeModal('transaction-modal');
    renderTransactions();
    showToast('Transaction saved', 'success');
  } catch (err) {
    showToast(err.message, 'error');
  }
};
```

## 6. MIGRATION STRATEGY

### 6.1 Principles

1. **Incremental**: One view at a time. No big-bang rewrite.
2. **Backward Compatible**: Legacy code continues to work during migration.
3. **Parallel Existence**: Old and new code coexist; old code removed only after new code verified.
4. **Test-Driven**: Each migrated view has characterization tests before and after.

### 6.2 Migration Phases

#### Phase 1: Component Extraction (No Behavior Change)

For each view:
1. Identify monolithic `renderX()` function.
2. Extract HTML generation into stateless components.
3. Keep `renderX()` as the entry point; it now uses components.
4. Test: UI renders identically before/after.

**Example**:
```javascript
// Before (legacy)
function renderTransactions() {
  const container = document.getElementById('transactions-container');
  container.innerHTML = '';
  for (const tx of window.transactions) {
    const div = document.createElement('div');
    div.className = 'tx-item';
    div.innerHTML = `<span>${tx.desc}</span>...`;
    container.appendChild(div);
  }
}

// After (componentized)
function renderTransactions() {
  const container = document.getElementById('transactions-container');
  const transactions = window.transactions || [];
  container.innerHTML = `
    <div class="transaction-list">
      ${transactions.map(tx => TransactionListItem({
        transaction: tx,
        onEdit: (id) => openTransactionModal(id),
        onDelete: (id) => confirmDeleteTransaction(id)
      })).join('')}
    </div>
  `;
}
```

#### Phase 2: Service Wiring

For each view:
1. Replace direct global array reads with service calls.
2. Replace direct `save()`/`remove()` calls with service calls.
3. Test: behavior identical before/after.

**Example**:
```javascript
// Before (legacy)
function confirmDeleteTransaction(id) {
  if (!confirm('Delete?')) return;
  window.transactions = window.transactions.filter(t => t.id !== id);
  window.save(SK.transactions, window.transactions);
  renderAll();
}

// After (service)
async function confirmDeleteTransaction(id) {
  if (!confirm('Delete?')) return;
  await window.TransactionService.remove(id);
  renderAll();
}
```

#### Phase 3: State Consolidation

For each view:
1. Move view state (active tab, filters, form values) to ApplicationState.
2. Components read from ApplicationState instead of globals.
3. Event handlers update ApplicationState instead of globals.

#### Phase 4: Modal Componentization

For each modal:
1. Extract modal HTML into `Modal` component.
2. Extract form into separate component.
3. Wire form submission to service.
4. Remove `openXModal()` / `closeXModal()` globals.

#### Phase 5: Index.html Split

When all views are componentized:
1. Extract inline scripts into `src/ui/` modules.
2. Replace inline `<script>` tags with `<script type="module" src="...">`.
3. Remove legacy global function exposure.

## 11. STATE MANAGEMENT

### 11.1 ApplicationState Integration

```javascript
// src/state/application-state.js
class ApplicationState {
  constructor() {
    this.state = {
      activeTab: 'home',
      activeMoneyPlace: 'konto',
      privacyMode: false,
      theme: 'system',
      transactionFilters: {
        monthKey: getCurrentMonthKey(),
        categoryId: null,
        accountId: null
      },
      modal: {
        isOpen: false,
        type: null,
        data: null
      }
    };
    this.listeners = new Set();
  }

  get(key) {
    return this.state[key];
  }

  set(key, value) {
    this.state[key] = value;
    this.emit(`change:${key}`, value);
  }

  on(event, callback) {
    this.listeners.add({ event, callback });
    return () => this.listeners.delete({ event, callback });
  }

  emit(event, data) {
    for (const { event: e, callback } of this.listeners) {
      if (e === event) callback(data);
    }
  }
}

window.AppState = new ApplicationState();
```

## 15. PERFORMANCE CONSIDERATIONS

### 15.1 InnerHTML vs DOM Manipulation

- **InnerHTML**: Faster for bulk updates, acceptable for MVP.
- **DOM manipulation**: More granular, better for frequent updates (future optimization).
- **Current choice**: InnerHTML for simplicity. Migrate to DOM if performance issues arise.

### 15.2 Render Optimization

```javascript
// Debounce rapid renders
function debouncedRender(fn, delay) {
  let timeout;
  return (...args) => {
    clearTimeout(timeout);
    timeout = setTimeout(() => fn(...args), delay);
  };
}

const debouncedRenderTransactions = debouncedRender(renderTransactions, 100);
```

### 15.3 Large Lists

For transaction lists > 100 items:
- Implement virtual scrolling (future).
- Current: pagination or "load more" button.
