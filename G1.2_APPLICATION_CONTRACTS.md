## 1. PURPOSE AND SCOPE

G1.2 defines the **application-layer operation contracts** for the MVP-1 greenfield Finora architecture. Each contract specifies the exact responsibilities, inputs, outputs, validation, error handling, and atomicity requirements for one application operation.

This document is the binding specification for G1.5 (Application Service Implementation) and G1.7 (UI Rewire). It does not redesign the domain model (G1.1), define module APIs (G1.3), plan repositories (G1.4), or specify storage (G1.6).

**Scope**: MVP-1 only. User/Profile, Accounts, Categories, Transactions, Budgets, Goals, Safe-to-Spend, and basic reports. V1+/plugin modules are explicitly excluded from this document.

---

## 2. ARCHITECTURE GUARDRAILS

These rules are non-negotiable for every contract defined below.

1. **Dependency direction**: UI → Application Services → Domain → Repository Interfaces → Storage. No reverse dependencies.
2. **Application layer orchestrates; it is not a second domain layer.** Domain rules live in `src/domain/` calculators. Application services wire inputs to calculators and repositories. They do not reimplement domain logic.
3. **Domain rules must not depend on IndexedDB, Firebase, UI, or framework code.** Domain calculators receive explicit inputs and return deterministic outputs.
4. **Repository interfaces must be storage-independent.** They accept a StorageAdapter in the constructor. No repository knows whether data lives in IndexedDB, Firebase, or a mock.
5. **Do not expose raw database records as the application API if that would leak persistence concerns.** Services return domain-shaped DTOs, not storage rows.
6. **Do not introduce generic "god service" or generic CRUD abstractions merely for convenience.** Each service method exists because the UI needs it.
7. **Do not design future V1+/plugin modules in detail.** Only the boundaries needed by MVP-1 are defined.
8. **Do not reintroduce the legacy monolithic `dbData` architecture.** Each entity has its own repository and storage key.
9. **Do not implement domain migrations.** Migration is a cross-cutting concern handled by the schema layer.
10. **Do not add unnecessary abstractions without a concrete MVP-1 use case.**

## 3. COMMON CONTRACTS

### 3.1 Error/Failure Contract

All application service methods return a **result envelope** or throw a typed error. The envelope pattern is preferred for operations that may partially fail or where the UI needs to distinguish "not found" from "storage error."

```javascript
// Success envelope
{ ok: true, data: <result> }

// Failure envelope
{ ok: false, error: { code: string, message: string, details?: any } }
```

**Error codes** (shared across all services):

| Code | Meaning | When Used |
|------|---------|-----------|
| `VALIDATION_FAILED` | Input does not satisfy schema | Repository or service validation rejects input |
| `NOT_FOUND` | Entity does not exist or belongs to another user | Repository returns null, service cannot proceed |
| `STORAGE_UNAVAILABLE` | StorageAdapter is not initialized or throws | Any repository call fails |
| `OWNERSHIP_VIOLATION` | Cross-user reference detected | Service or repository validates userId mismatch |
| `ARCHIVED_ENTITY` | Operation attempted on an archived entity where prohibited | Lifecycle rule blocks the operation |
| `CIRCULAR_REFERENCE` | Operation would create a cycle (e.g., goal referencing itself) | Validation detects cycle |
| `DUPLICATE_DETECTED` | Informational only; never blocks creation | Duplicate detection warning |
| `REBUILD_REQUIRED` | Goal.current cache is stale and must be rebuilt before update | Rebuild path triggered |

Services may also throw for programmer errors (missing calculator, missing dependency) — these are **not** user-facing failures.

### 3.2 Ownership Validation

Every write operation MUST enforce that the `userId` on the entity being written matches the `userId` of the authenticated session. This is enforced at the **repository boundary** for direct writes, and at the **service boundary** for cross-entity operations.

**Repository-level**: `save(entity)` rejects with `OWNERSHIP_VIOLATION` if `entity.userId !== currentUserId`.

**Service-level**: When an operation references another entity (e.g., `Transaction.accountId` → `Account.id`), the service MUST verify that the referenced entity's `userId` matches the current user before proceeding. This is the **Same-user ownership invariant** from G1.1 §2.10.

### 3.3 Archived Entity Rules

| Entity | Archived Behavior |
|--------|------------------|
| Account | Excluded from current balances, net worth, and Safe-to-Spend. Retains all historical transactions. New transactions MUST NOT reference an archived `accountId`. |
| Category | Hidden from selection in transaction entry and reports. Existing transactions retain their `categoryId`. System categories cannot be archived. |
| Goal | Excluded from Safe-to-Spend and goal reports. `current` is preserved. Existing goal-contribution transactions remain in the ledger. |
| Transaction | Excluded from all current financial calculations: balances, reports, Safe-to-Spend, budget progress, and income/expense statistics. Remains in persistent record. |

**Application service rule**: When a query operation returns data that includes archived entities (e.g., historical reports), the service MUST document whether archived records are included. Default queries exclude archived records unless explicitly requested.

### 3.4 Atomicity Rules

| Operation | Must Be Atomic | Rationale |
|-----------|---------------|-----------|
| Transaction create/update/delete | Yes | Ledger integrity; partial writes corrupt balances |
| Goal contribution transaction + current update | Yes | Invariant: `current` must equal transaction sum in same unit of work |
| Account archive | Yes | Balance exclusion must be immediate and consistent |
| Category archive | No (soft flag) | Single-field update; no cross-entity invariant |
| Budget create/update/delete | Yes | Budget progress depends on consistent budget set |
| Safe-to-Spend computation | N/A (query) | Read-only; no persistence |
| Goal.current rebuild | Yes | Must replace stale cache atomically; old value must not persist alongside new |

### 3.5 Command vs Query Classification

| Command | Query |
|---------|-------|
| `createAccount` | `getProfile` |
| `updateAccount` | `getAccount` |
| `archiveAccount` | `getActiveAccounts` |
| `createCategory` | `getSystemCategories` |
| `archiveCategory` | `getTransactionsByMonth` |
| `createTransaction` | `getTransactionsByAccount` |
| `updateTransaction` | `getBudgetProgress` |
| `archiveTransaction` | `getActiveGoals` |
| `createBudget` | `getGoalEta` |
| `updateBudget` | `getRequiredDepositsThisMonth` |
| `archiveBudget` | `computeSafeToSpend` |
| `createGoal` | `computeForCurrentState` |
| `updateGoal` | `getMonthlySummary` |
| `depositToGoal` | `getMonthCategoryBreakdown` |
| `archiveGoal` | `getAccountBalance` |
| `rebuildGoalCurrent` | — |

## 4. USER / PROFILE OPERATIONS

### 4.1 getProfile

**Responsibility**: Return the current user's profile settings.

**Input contract**: `{ userId: string }`

**Output contract**: `UserProfile` entity (G1.1 §2.2).

**Validation responsibility**: Service validates `userId` is non-empty. Repository does not validate.

**Domain/business-rule responsibility**: None. Profile is a settings container.

**Repository dependencies**: None for read. Profile is typically loaded at session start and cached in ApplicationState.

**Error/failure contract**: Throws `NOT_FOUND` if no profile exists for the user.

**Atomicity**: N/A (query).

**Command/query**: Query.

**Ownership/lifecycle requirements**: Profile is created at user bootstrap. `userId` is immutable. `settings` are user-editable. `excludeInvestmentsFromNetWorth` has no effect in MVP-1.

## 5. ACCOUNT OPERATIONS

### 5.1 createAccount

**Responsibility**: Create a new account for the current user.

**Input contract**:
```typescript
{
  userId: string,
  name: string,           // 1-100 chars
  type: 'cash' | 'bank' | 'savings',
  icon: string,           // Lucide icon name
  color: string,          // Hex color
  openingBalance?: number // optional; positive, zero, or negative
}
```

**Output contract**: `Account` entity with generated `id`, `userId`, `archived: false`, `createdAt`, `updatedAt`.

**Validation responsibility**:
- Service validates: `name` non-empty, `type` in allowed set, `color` is valid hex, `icon` is non-empty.
- Service validates: `openingBalance` is a finite number (positive, zero, or negative).
- Service enforces: MVP-1 does NOT allow `type: 'investment'`. If provided, reject with `VALIDATION_FAILED`.

**Domain/business-rule responsibility**:
- Default accounts: Konto (`bank`), Skarbonka (`savings`), Inne (`cash`). The service must seed these defaults if they do not exist.
- `investment` account type is V1+ only. MVP-1 must NOT create, validate, render, or depend on it.
- If `openingBalance !== 0`, the service MUST also create an opening-balance transaction (see §6.7).
- Positive opening balance → income transaction with `metadata.openingBalance = true`.
- Negative opening balance → expense transaction with `metadata.openingBalance = true` and `amount = abs(openingBalance)`.
- Zero opening balance → no opening-balance transaction required.

**Repository dependencies**: `AccountRepository.save(account)`. Must verify repository is initialized for `userId`.

**Error/failure contract**:
- `VALIDATION_FAILED`: Invalid input shape.
- `STORAGE_UNAVAILABLE`: Repository cannot persist.
- If opening-balance transaction creation fails, the account creation MUST be rolled back. Return `STORAGE_UNAVAILABLE` with details.

**Atomicity**: Yes. Account creation and opening-balance transaction creation (if applicable) must succeed or fail together.

**Command/query**: Command.

**Ownership/lifecycle requirements**:
- `userId` is set at creation and never changes.
- `archived` defaults to `false`.
- Accounts may be archived with non-zero balance. The balance is not reset.
- New transactions MUST NOT reference an archived `accountId`. The service enforces this by rejecting transactions that target archived accounts.

### 5.2 getAccount

**Responsibility**: Return a single account by id.

**Input contract**: `{ accountId: string }`

**Output contract**: `Account` entity or `null`.

**Validation responsibility**: Service validates `accountId` is non-empty.

**Domain/business-rule responsibility**: None.

**Repository dependencies**: `AccountRepository.findById(accountId)`.

**Error/failure contract**: Returns `null` if not found or if account belongs to another user (repository filters by userId implicitly via storage key).

**Atomicity**: N/A (query).

**Command/query**: Query.

### 5.3 getActiveAccounts

**Responsibility**: Return all non-archived accounts for the current user.

**Input contract**: `{ userId: string }`

**Output contract**: `Account[]` where `archived === false`.

**Validation responsibility**: None.

**Domain/business-rule responsibility**: None.

**Repository dependencies**: `AccountRepository.loadAll()` with in-memory filter for `archived === false`.

**Error/failure contract**: Returns empty array if none exist. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 5.4 updateAccount

**Responsibility**: Update mutable fields on an existing account.

**Input contract**:
```typescript
{
  accountId: string,
  updates: {
    name?: string,
    icon?: string,
    color?: string,
    type?: 'cash' | 'bank' | 'savings'
  }
}
```

**Output contract**: Updated `Account` entity.

**Validation responsibility**:
- Service validates `accountId` exists.
- Service validates `name` non-empty if provided.
- Service validates `type` in allowed set if provided.
- Service enforces: `type: 'investment'` is rejected in MVP-1.

**Domain/business-rule responsibility**:
- `userId` and `id` are immutable.
- Changing `type` does not retroactively adjust balances; it affects future calculations.
- `archived` is NOT updated via this method; use `archiveAccount`.

**Repository dependencies**: `AccountRepository.findById(accountId)` then `AccountRepository.save(updated)`.

**Error/failure contract**:
- `NOT_FOUND`: Account does not exist.
- `VALIDATION_FAILED`: Invalid field values.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes. Read-modify-write is atomic at the repository level.

**Command/query**: Command.

**Ownership/lifecycle requirements**: `userId` is verified at load time. Account cannot be transferred between users.

### 5.5 archiveAccount

**Responsibility**: Mark an account as archived.

**Input contract**: `{ accountId: string }`

**Output contract**: Updated `Account` entity with `archived: true`.

**Validation responsibility**:
- Service validates account exists.
- Service validates account is not already archived (idempotent — if already archived, return success without error).

**Domain/business-rule responsibility**:
- Archived accounts are excluded from current balances, net worth, and Safe-to-Spend.
- Historical transactions for the account remain queryable.
- Non-zero balance accounts MAY be archived. The balance is not reset.
- After archiving, new transactions referencing this `accountId` are rejected by the transaction creation service.

**Repository dependencies**: `AccountRepository.findById(accountId)` then `AccountRepository.save({ ...existing, archived: true })`.

**Error/failure contract**:
- `NOT_FOUND`: Account does not exist.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes. Single-field update.

**Command/query**: Command.

## 6. CATEGORY OPERATIONS

### 6.1 createCategory

**Responsibility**: Create a new user category.

**Input contract**:
```typescript
{
  userId: string,
  name: string,           // 1-50 chars
  type: 'income' | 'expense',
  icon: string,
  color: string,
  parentId?: string | null // MUST be null in MVP-1; reserved for V1+
}
```

**Output contract**: `Category` entity with generated `id`, `userId`, `isSystem: false`, `createdAt`, `updatedAt`.

**Validation responsibility**:
- Service validates `name` non-empty, `type` in allowed set.
- Service validates `parentId` is `null` or not provided. If provided and non-null, reject with `VALIDATION_FAILED`. In MVP-1, `parentId` MUST remain `null`.
- Service validates `icon` and `color` are non-empty.

**Domain/business-rule responsibility**:
- System categories are pre-seeded and cannot be deleted. User categories can be created/edited/archived.
- Archiving hides the category from selection but preserves existing transactions.
- `type` must match transaction type for budgets.

**Repository dependencies**: `CategoryRepository.save(category)`. Verify repository is initialized for `userId`.

**Error/failure contract**:
- `VALIDATION_FAILED`: Invalid input or `parentId` is non-null in MVP-1.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes.

**Command/query**: Command.

**Ownership/lifecycle requirements**:
- `userId` is set at creation and never changes.
- `isSystem` is set at seed time only. User-created categories have `isSystem: false`.
- System categories cannot be archived. The service enforces this.

### 6.2 getSystemCategories

**Responsibility**: Return all system categories for the current user.

**Input contract**: `{ userId: string }`

**Output contract**: `Category[]` where `isSystem === true`.

**Validation responsibility**: None.

**Domain/business-rule responsibility**:
- System categories provide stable identity for domain rules via `systemRole`.
- System categories must never be identified by display name in domain logic. All rules use `id` or `systemRole`.

**Repository dependencies**: `CategoryRepository.findSystem()`.

**Error/failure contract**: Returns empty array if none exist after successful read. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 6.3 archiveCategory

**Responsibility**: Archive a user category.

**Input contract**: `{ categoryId: string }`

**Output contract**: Updated `Category` entity with `archived: true`.

**Validation responsibility**:
- Service validates category exists.
- Service validates category is a user category (`isSystem === false`). System categories cannot be archived.
- Service validates no active budgets reference this category. If a budget exists, archive is rejected with `VALIDATION_FAILED`.

**Domain/business-rule responsibility**:
- Archived categories are hidden from selection in transaction entry and reports.
- Existing transactions retain their `categoryId`.
- An archived category is not shown in standard category breakdowns unless explicitly requested.

**Repository dependencies**: `CategoryRepository.findById(categoryId)` then `CategoryRepository.save({ ...existing, archived: true })`.

**Error/failure contract**:
- `NOT_FOUND`: Category does not exist.
- `VALIDATION_FAILED`: System category or referenced by active budget.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes.

**Command/query**: Command.

## 7. TRANSACTION OPERATIONS

### 7.1 createTransaction

**Responsibility**: Create a new transaction and update derived state atomically.

**Input contract**:
```typescript
{
  userId: string,
  accountId: string,
  amount: number,          // > 0, always positive
  type: 'income' | 'expense',
  categoryId?: string | null,
  description: string,     // 0-500 chars
  date: string,            // YYYY-MM-DD
  metadata?: Record<string, any>,
  // opening balance fields
  isOpeningBalance?: boolean,
  openingBalanceCategoryId?: string
}
```

**Output contract**: `Transaction` entity with generated `id`, `userId`, `createdAt`, `updatedAt`.

**Validation responsibility**:
- Service validates: `accountId` exists and is owned by `userId`.
- Service validates: `accountId` is NOT archived. Reject with `ARCHIVED_ENTITY` if archived.
- Service validates: `amount` is a positive number.
- Service validates: `type` is `'income'` or `'expense'`. MVP-1 has no `'transfer'` type.
- Service validates: `date` matches `YYYY-MM-DD`.
- Service validates: `description` is a string (empty string allowed).
- Service validates: `categoryId` if provided must exist and be owned by `userId`.
- Service validates: `categoryId` must not reference an archived category.
- If `isOpeningBalance` is true, service validates `openingBalanceCategoryId` is a system category with `systemRole === 'opening-balance'`.
- **Duplicate detection is informational only.** The service MAY check for duplicates and return `DUPLICATE_DETECTED` in the result envelope, but MUST NOT block creation.

**Domain/business-rule responsibility**:
- `amount` is always positive. Sign is determined by `type`.
- `notes` is always a string (empty if none). `tags` is always an array. `metadata` is always an object.
- **Opening-balance transactions**: If `isOpeningBalance` is true, the transaction is created with `metadata.openingBalance = true`. These transactions affect the account balance but are excluded from income/expense statistics and Safe-to-Spend.
- **Goal-contribution transactions**: If `metadata.goalId` is set, the transaction must use a category with `systemRole === 'savings'`. The service MUST update `Goal.current` atomically with transaction creation.
- **Positive amounts**: All transaction amounts are positive. For expenses, the type field indicates direction.

**Repository dependencies**: `TransactionRepository.save(transaction)`. May also call `GoalRepository.save(goal)` if goal contribution.

**Error/failure contract**:
- `VALIDATION_FAILED`: Invalid input, archived account/category, or `parentId` provided.
- `NOT_FOUND`: Account or category does not exist.
- `OWNERSHIP_VIOLATION`: Account or category belongs to another user.
- `ARCHIVED_ENTITY`: Account is archived.
- `STORAGE_UNAVAILABLE`: Persistence failure.
- `DUPLICATE_DETECTED`: Informational only; transaction is still created. Envelope includes `{ ok: true, data: transaction, warning: 'DUPLICATE_DETECTED' }`.

**Atomicity**: Yes. Transaction creation and any side effects (goal.current update) must succeed or fail together. If the transaction is saved but goal update fails, the service MUST roll back the transaction and return `STORAGE_UNAVAILABLE`.

**Command/query**: Command.

**Ownership/lifecycle requirements**:
- `userId` is immutable.
- `accountId`, `categoryId`, and `metadata` links MUST resolve to entities owned by the same `userId`.
- Transactions are soft-deleted via `archived: true`. They are never physically deleted.

### 7.2 updateTransaction

**Responsibility**: Update mutable fields on an existing transaction.

**Input contract**:
```typescript
{
  transactionId: string,
  updates: {
    accountId?: string,
    amount?: number,       // > 0
    type?: 'income' | 'expense',
    categoryId?: string | null,
    description?: string,
    date?: string,         // YYYY-MM-DD
    metadata?: Record<string, any>
  }
}
```

**Output contract**: Updated `Transaction` entity.

**Validation responsibility**:
- Service validates transaction exists.
- Service validates `accountId` (if changed) is active and owned by `userId`.
- Service validates `amount` > 0 if provided.
- Service validates `type` in allowed set if provided.
- Service validates `categoryId` (if changed) is not archived.
- Service validates `date` format if provided.
- **Archiving is NOT performed via this method.** Use `archiveTransaction` for lifecycle changes.

**Domain/business-rule responsibility**:
- **Goal-contribution correction**: If the transaction has `metadata.goalId`, the service MUST recalculate `Goal.current` to reflect the delta. The invariant is `current = sum(qualifying transactions)`. Correction adjusts by delta.
- **Opening-balance transactions**: Cannot be converted to non-opening-balance or vice versa via update. Opening-balance status is set at creation only.
- **Duplicate detection**: Informational only after update as well.

**Repository dependencies**: `TransactionRepository.findById(transactionId)` then `TransactionRepository.save(updated)`. May call `GoalRepository.save(goal)` for goal.current adjustment.

**Error/failure contract**:
- `NOT_FOUND`: Transaction does not exist.
- `VALIDATION_FAILED`: Invalid field values.
- `OWNERSHIP_VIOLATION`: Transaction belongs to another user.
- `ARCHIVED_ENTITY`: Target account is archived.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes. If transaction update succeeds but goal.current adjustment fails, the transaction update MUST be rolled back.

**Command/query**: Command.

### 7.3 archiveTransaction

**Responsibility**: Mark a transaction as archived.

**Input contract**: `{ transactionId: string }`

**Output contract**: Updated `Transaction` entity with `archived: true`.

**Validation responsibility**:
- Service validates transaction exists.
- Service validates transaction is not already archived (idempotent if already archived).

**Domain/business-rule responsibility**:
- Archived transactions are excluded from all current financial calculations: balances, reports, Safe-to-Spend, budget progress, and income/expense statistics.
- If the transaction is a goal-contribution transaction (`metadata.goalId` set and `category.systemRole === 'savings'`), the service MUST decrement `Goal.current` by the transaction's `amount` atomically.
- The transaction persists in the record and may be included in historical queries if the caller explicitly requests archived records.

**Repository dependencies**: `TransactionRepository.findById(transactionId)` then `TransactionRepository.save({ ...existing, archived: true })`. May call `GoalRepository.save(goal)` for goal.current adjustment.

**Error/failure contract**:
- `NOT_FOUND`: Transaction does not exist.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes. Transaction archive and goal.current adjustment (if applicable) must succeed or fail together.

**Command/query**: Command.

### 7.4 getTransactionsByMonth

**Responsibility**: Return all non-archived transactions for a given month.

**Input contract**: `{ userId: string, monthKey: string }` where `monthKey` is `YYYY-MM`.

**Output contract**: `Transaction[]` sorted by `date` ascending, then `createdAt` ascending.

**Validation responsibility**: Service validates `monthKey` format.

**Domain/business-rule responsibility**:
- Excludes archived transactions by default.
- Does NOT exclude `metadata.excluded` transactions (that flag does not exist in greenfield; use `archived`).
- Opening-balance transactions ARE included in the result set but are flagged in `metadata.openingBalance`.

**Repository dependencies**: `TransactionRepository.findByMonth(monthKey)` with userId filter.

**Error/failure contract**: Returns empty array if none exist after successful read. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 7.5 getTransactionsByAccount

**Responsibility**: Return all non-archived transactions for a given account.

**Input contract**: `{ accountId: string }`

**Output contract**: `Transaction[]` sorted by `date` descending.

**Validation responsibility**: Service validates `accountId` exists.

**Domain/business-rule responsibility**: None beyond archived exclusion.

**Repository dependencies**: `TransactionRepository.findByAccount(accountId)`.

**Error/failure contract**: Returns empty array if none exist after successful read. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

## 8. BUDGET OPERATIONS

### 8.1 createBudget

**Responsibility**: Create a new budget.

**Input contract**:
```typescript
{
  userId: string,
  categoryId: string,
  amount: number           // > 0
}
```

**Output contract**: `Budget` entity with generated `id`, `userId`, `period: 'monthly'`, `createdAt`, `updatedAt`.

**Validation responsibility**:
- Service validates `categoryId` exists, is owned by `userId`, and is not archived.
- Service validates `amount` > 0.
- Service validates: one budget per category per user. If a budget already exists for this category, reject with `VALIDATION_FAILED`.

**Domain/business-rule responsibility**:
- MVP-1 budgets are monthly-only. The service enforces `period: 'monthly'` and rejects any other period.
- Budget progress is derived: sum of expenses in category for the month.

**Repository dependencies**: `BudgetRepository.save(budget)`. `CategoryRepository.findById(categoryId)` for validation.

**Error/failure contract**:
- `VALIDATION_FAILED`: Duplicate budget, invalid amount, or archived category.
- `NOT_FOUND`: Category does not exist.
- `OWNERSHIP_VIOLATION`: Category belongs to another user.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes.

**Command/query**: Command.

### 8.2 getBudgetProgress

**Responsibility**: Calculate budget progress for a given month.

**Input contract**: `{ budgetId: string, monthKey: string }`

**Output contract**:
```typescript
{
  id: string,
  categoryId: string,
  amount: number,          // budget limit
  spent: number,           // sum of expenses for category in month
  remaining: number,       // amount - spent
  overBudget: boolean      // spent > amount
}
```

**Validation responsibility**: Service validates `budgetId` exists.

**Domain/business-rule responsibility**:
- Budget progress is derived from transactions, not persisted.
- Excludes archived transactions.
- Excludes opening-balance transactions.
- Excludes goal-contribution transactions (identified by `category.systemRole === 'savings'`).
- Uses `TransactionRepository.findByMonth(monthKey)` and filters by `categoryId` and `type === 'expense'`.

**Repository dependencies**: `BudgetRepository.findById(budgetId)`, `TransactionRepository.findByMonth(monthKey)`.

**Error/failure contract**:
- `NOT_FOUND`: Budget does not exist.
- `STORAGE_UNAVAILABLE`: Persistence failure during read.

**Atomicity**: N/A (query). Reads are consistent at the time of execution.

**Command/query**: Query.

### 8.3 updateBudget

**Responsibility**: Update the amount on an existing budget.

**Input contract**: `{ budgetId: string, amount: number }`

**Output contract**: Updated `Budget` entity.

**Validation responsibility**: Service validates `amount` > 0.

**Domain/business-rule responsibility**: None beyond amount validation.

**Repository dependencies**: `BudgetRepository.findById(budgetId)` then `BudgetRepository.save(updated)`.

**Error/failure contract**:
- `NOT_FOUND`: Budget does not exist.
- `VALIDATION_FAILED`: `amount` <= 0.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes.

**Command/query**: Command.

### 8.4 archiveBudget

**Responsibility**: Mark a budget as archived.

**Input contract**: `{ budgetId: string }`

**Output contract**: Updated `Budget` entity with `archived: true`.

**Validation responsibility**:
- Service validates budget exists.
- Service validates budget is not already archived (idempotent if already archived).

**Domain/business-rule responsibility**:
- An archived budget is excluded from budget progress calculations.
- The spending limit for that category is no longer enforced.
- Existing transactions are not affected. Historical budget progress becomes inaccessible.
- **Note**: The G1.1 domain model does not define an `archived` field on `Budget`. The minimum lifecycle rule is: the service maintains an archived flag locally (or via a soft-delete marker in storage). The repository supports this operation without schema changes. Future schema versions may add an explicit `archived` field.

### 9.2 updateGoal

**Responsibility**: Update mutable fields on an existing goal.

### 9.3 depositToGoal

**Responsibility**: Create a goal-contribution transaction and update `Goal.current` atomically.

**Input contract**:
```typescript
{
  userId: string,
  goalId: string,
  accountId: string,       // source spendable account
  amount: number,          // > 0
  date: string,            // YYYY-MM-DD
  description?: string
}
```

**Output contract**: `{ transaction: Transaction, goal: Goal }`

**Validation responsibility**:
- Service validates `goalId` exists, is owned by `userId`, and is not archived.
- Service validates `accountId` exists, is owned by `userId`, and is not archived.
- Service validates `amount` > 0.
- Service validates `date` format.
- Service validates the goal has not reached its target. If `amount > goal.target - goal.current`, reject with `VALIDATION_FAILED`.

**Domain/business-rule responsibility**:
- **Invariant**: `current` MUST equal the sum of all non-archived transactions where `metadata.goalId === goal.id` and `category.systemRole === 'savings'`. This is the single source of truth.
- The service creates a single `Transaction` with:
  - `type='expense'`
  - `accountId` = source spendable account
  - `categoryId` = system category with `systemRole === 'savings'`
  - `metadata.goalId = goalId`
  - `amount` = contribution amount
- The service updates `Goal.current` by adding `amount` in the same unit of work. **No clamping is applied.** `current` is set to the exact sum of all qualifying transactions.
- The transaction reduces the source account balance via normal balance calculation.
- Goal-contribution transactions are excluded from ordinary expense reports and budget progress by `category.systemRole === 'savings'`, not by display name.

**Repository dependencies**: `TransactionRepository.save(transaction)`, `GoalRepository.save(goal)`.

**Error/failure contract**:
- `NOT_FOUND`: Goal or account does not exist.
- `VALIDATION_FAILED`: Invalid amount, archived account/goal, or goal already at target.
- `OWNERSHIP_VIOLATION`: Goal or account belongs to another user.
- `ARCHIVED_ENTITY`: Account or goal is archived.
- `STORAGE_UNAVAILABLE`: Persistence failure. If transaction is saved but goal update fails, the service MUST roll back the transaction.

**Atomicity**: Yes. Transaction creation and `Goal.current` update are a single atomic operation.

**Command/query**: Command.

**Validation responsibility**:

**Domain/business-rule responsibility**:

- `current` value is preserved.
- Existing goal-contribution transactions remain in the ledger and retain `metadata.goalId`.
- Goal-contribution transactions continue to be excluded from ordinary expense reports by their category system role.

**Repository dependencies**: `GoalRepository.findById(goalId)` then `GoalRepository.save({ ...existing, archived: true })`.

**Error/failure contract**:

### 9.5 rebuildGoalCurrent

**Responsibility**: Recalculate `Goal.current` from the transaction ledger and update atomically.

**Input contract**: `{ goalId: string }`

**Output contract**: `{ goal: Goal, rebuilt: boolean }` where `rebuilt` indicates whether the value changed.

**Validation responsibility**:
- Service validates goal exists.

**Domain/business-rule responsibility**:
- **Invariant**: `current` MUST equal `sum` of all non-archived transactions where `metadata.goalId === goal.id` and `category.systemRole === 'savings'`.
- The service recalculates `current` by summing all qualifying transactions across all accounts for the user.
- **No clamping is applied.** `current` is set to the exact sum.
- `currentLastRebuiltAt` is set to the current ISO datetime.
- If `current` was already correct, `rebuilt` is `false` and `currentLastRebuiltAt` is still updated to reflect the rebuild attempt.

**Repository dependencies**: `GoalRepository.findById(goalId)`, `TransactionRepository.loadAll()` (or equivalent), `GoalRepository.save(goal)`.

**Error/failure contract**:
- `NOT_FOUND`: Goal does not exist.
- `STORAGE_UNAVAILABLE`: Persistence failure.

**Atomicity**: Yes. The old cache is replaced atomically.

**Command/query**: Command.

**Domain/business-rule responsibility**: None.

**Repository dependencies**: `GoalRepository.loadAll()` with in-memory filter.

**Error/failure contract**: Returns empty array if none exist after successful read. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 9.7 getGoalEta

**Responsibility**: Estimate goal completion date.

**Input contract**: `{ goalId: string, currentDate?: Date }`

**Output contract**:
```typescript
{
  goalId: string,
  remaining: number,       // target - current
  monthsNeeded: number | null,
  avgPerMonth: number | null,
  etaDate: string | null,  // ISO date YYYY-MM-DD
  unknown: boolean         // true if cannot estimate
}
```

**Validation responsibility**: Service validates `goalId` exists.

**Domain/business-rule responsibility**:
- Uses only non-archived goal-contribution transactions (`metadata.goalId === goal.id`, `category.systemRole === 'savings'`, `!archived`).
- `monthsSpan` = calendar months from first deposit to `currentDate` (minimum 1).
- `avgPerMonth` = totalSaved / monthsSpan.
- If `avgPerMonth <= 0`, returns `{ unknown: true }`.
- `monthsNeeded = Math.ceil(remaining / avgPerMonth)`.
- `etaDate` = first day of month `currentDate + monthsNeeded`.
- If `remaining <= 0`, returns `{ unknown: true, reason: 'goal_reached' }`.

**Repository dependencies**: `GoalRepository.findById(goalId)`, `TransactionRepository.loadAll()` filtered for goal contributions.

**Error/failure contract**:
- `NOT_FOUND`: Goal does not exist.
- Returns `{ unknown: true }` for unreachable goals.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 9.8 getRequiredDepositsThisMonth

**Responsibility**: Compute the total monthly goal deposits required for Safe-to-Spend.

**Input contract**: `{ goals: Goal[], currentDate: Date }`

**Output contract**: `number` — sum of required monthly deposits for goals with deadline and remaining > 0.

**Validation responsibility**: None.

**Domain/business-rule responsibility**:
- Only goals with `deadline` and `remaining > 0` are included.
- Past deadline: entire remaining amount is urgent (added in full).
- Future deadline: `remaining / monthsLeft` where `monthsLeft` is at least 1.
- `monthsLeft` = `(deadlineYear - currentYear) * 12 + (deadlineMonth - currentMonth) + 1`.
- Archived goals are excluded.
- This is the `goalRequirements` input to Safe-to-Spend.

**Repository dependencies**: None if goals are passed in. If fetching from repository, uses `GoalRepository.loadAll()`.

**Error/failure contract**: Returns `0` if no goals qualify after successful read. Throws `STORAGE_UNAVAILABLE` if repository read fails.

**Atomicity**: N/A (query).

**Command/query**: Query.

## 10. SAFE-TO-SPEND OPERATIONS

### 10.1 computeSafeToSpend

**Responsibility**: Compute MVP-1 Safe-to-Spend using explicit inputs.

**Input contract**:
```typescript
{
  freeFunds: number,       // sum of active bank + cash account balances
  goalsReq: number,        // from getRequiredDepositsThisMonth
  daysLeft: number         // days remaining in current month
}
```

**Output contract**:
```typescript
{
  freeFunds: number,
  goalsReq: number,
  daysLeft: number,         // clamped to >= 1
  safeTotal: number,        // freeFunds - goalsReq
  perDay: number            // safeTotal / daysLeft; always finite
}
```

**Validation responsibility**: None. The service clamps `daysLeft` to `>= 1` before calling the calculator.

**Domain/business-rule responsibility**:
- **MVP-1 formula**: `safeTotal = freeFunds - goalsReq`. `upcomingBills` is intentionally deferred to MVP-2.
- `daysLeft` is clamped to `Math.max(1, daysLeft)` before computation. The output `daysLeft` reflects the clamped value.
- `safeTotal` can be negative (user is over-committed).
- `perDay` is always finite. If the raw input `daysLeft` is `0` or negative, `perDay = safeTotal / 1`.
- Safe-to-Spend does NOT subtract `upcomingBills` in MVP-1. This is an explicit product decision.
- Safe-to-Spend does NOT include `savings` accounts in `freeFunds`. Only `bank` and `cash` accounts contribute.
- Safe-to-Spend uses `(goal.target - goal.current) / monthsLeft` for goals with deadlines and remaining > 0. Because `current` already reflects the reduced account balance, the remaining requirement is not double-counted.

**Repository dependencies**: None. This is a pure domain calculator. The application service aggregates inputs from balance and goal services.

**Error/failure contract**: Never throws. `daysLeft` is clamped before computation, so `perDay` is always finite. Returns negative `perDay` when over-committed.

**Atomicity**: N/A (query).

**Command/query**: Query.

### 10.2 computeForCurrentState (Application Service)

**Responsibility**: Compose explicit inputs from greenfield repositories and delegate to `SafeToSpendCalculator`.

**Input contract**: `{ currentDate?: Date }`

**Output contract**: Same as `computeSafeToSpend`.

**Validation responsibility**: None.

**Domain/business-rule responsibility**:
- Reads `freeFunds` from the sum of active `bank` and `cash` account balances via `AccountRepository` and `TransactionRepository`.
- Reads `goalsReq` from `getRequiredDepositsThisMonth`.
- Computes `daysLeft` from `currentDate` and clamps to `>= 1`.
- Delegates to `SafeToSpendCalculator.compute()` with explicit inputs.
- **Must NOT read legacy global state, `dbData`, or migration-bridge architecture.**

**Repository dependencies**: `AccountRepository.loadAll()`, `TransactionRepository.findByAccount(accountId)`, `GoalRepository.loadAll()`.

**Error/failure contract**:
- `STORAGE_UNAVAILABLE`: Any repository read fails.
- Throws if `SafeToSpendCalculator` is not available.

**Atomicity**: N/A (query).

**Command/query**: Query.

## 12. CROSS-CUTTING BOUNDARIES

### 12.1 Derived Calculations vs Persisted State

| Data | Persisted? | Owner | Notes |
|------|-----------|-------|-------|
| Account balance | No (derived) | Domain calculator | Computed from transactions on demand |
| Safe-to-Spend | No (derived) | Domain calculator + service | Computed from balances and goals |
| Budget progress | No (derived) | Service | Computed from transactions and budget |
| Goal ETA | No (derived) | Domain calculator | Computed from goal and transactions |
| `Goal.current` | **Yes** (rebuildable cache) | Service + invariant | Must equal sum of qualifying transactions |
| Category breakdown | No (derived) | Service | Computed from transactions |
| Monthly summary | No (derived) | Service | Computed from transactions |

**Rule**: Derived values are never persisted unless explicitly marked as rebuildable cache (only `Goal.current` in MVP-1). The application service computes derived values on demand by calling domain calculators.

### 12.2 Opening Balance Boundary

Opening balances are created at account creation time via `createAccount` with `openingBalance > 0`. The service:
1. Creates the account.
2. Creates an opening-balance transaction with `metadata.openingBalance = true` and `category.systemRole === 'opening-balance'`.
3. Both operations are atomic.

Opening-balance transactions:
- Affect the account balance (normal inclusion).
- Are excluded from income/expense statistics.
- Are excluded from Safe-to-Spend.
- Are included in the transaction history for the account.
- Cannot be converted to/from regular transactions via `updateTransaction`.

### 12.3 Goal Contribution Boundary

Goal contributions flow through `depositToGoal` only. They are NOT created via `createTransaction` directly by the UI. The service:
1. Validates the goal and source account.
2. Creates the transaction with the correct category (`systemRole === 'savings'`) and `metadata.goalId`.
3. Updates `Goal.current` atomically by adding the transaction amount. **No clamping is applied.**

The `current` field is a **rebuildable cache**. The invariant is:
```
current == sum(transactions WHERE metadata.goalId === goal.id AND category.systemRole === 'savings' AND !archived)
```

Any deviation triggers `rebuildGoalCurrent`.

### 12.4 Transaction Correction/Deletion/Archiving Boundary

| Action | Effect on `Goal.current` | Effect on Balance |
|--------|-------------------------|-------------------|
| Create goal-contribution tx | +amount (atomic) | -amount (source account) |
| Update goal-contribution tx | delta (newAmount - oldAmount) | delta if account changes |
| Archive goal-contribution tx | -amount | -amount (excluded from balance) |
| Delete goal-contribution tx | -amount | +amount (removed from ledger) |
| Rebuild `Goal.current` | Full recalculation | No effect |

**Rule**: Any mutation to a goal-contribution transaction MUST adjust `Goal.current` atomically. If the transaction mutation fails, `current` is unchanged. If the transaction mutation succeeds but `current` update fails, the transaction MUST be rolled back.

### 12.5 Account/Category/Goal Reference Boundary

The application service enforces cross-entity ownership at the service layer:

```typescript
// Pattern for all operations that reference another entity
async function validateReference<T>(
  repo: Repository<T>,
  id: string,
  userId: string,
  entityName: string
): Promise<T> {
  const entity = await repo.findById(id);
  if (!entity) throw NOT_FOUND;
  if (entity.userId !== userId) throw OWNERSHIP_VIOLATION;
  return entity;
}
```

**Archived references**:
- Transactions MUST NOT reference archived accounts.
- Transactions SHOULD NOT reference archived categories (the UI hides them, but the service validates).
- Budgets MUST NOT reference archived categories (enforced at creation).

### 12.6 Safe-to-Spend MVP-1 Formula Boundary

The Safe-to-Spend formula in MVP-1 is:

```
safeTotal = freeFunds - goalsReq
perDay = safeTotal / daysLeft (clamped to daysLeft >= 1)
```

**What is included in `freeFunds`**:
- Active `bank` accounts.
- Active `cash` accounts.
- `savings` accounts are EXCLUDED.

**What is NOT in MVP-1 Safe-to-Spend**:
- `upcomingBills` (requires RecurringRule, deferred to MVP-2).
- `investment` accounts (V1+ only).
- Net worth (V1+).

This is an explicit product decision from G0.4. The application service must not silently add bills or other terms.

### 12.7 Positive Amount Boundary

All monetary amounts in MVP-1 are **positive numbers**. Sign is encoded in the entity field:
- Transaction `type` field: `'income'` adds to balance, `'expense'` subtracts.
- Account balances: computed as `sum(income amounts) - sum(expense amounts)`.
- Goal `current`: always >= 0.
- Budget `amount`: always > 0.

Negative amounts are rejected at validation. Legacy negative amounts are normalized by the import layer, not the domain model.
