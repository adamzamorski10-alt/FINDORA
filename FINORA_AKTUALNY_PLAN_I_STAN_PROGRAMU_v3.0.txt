============================================================
1. CEL DOKUMENTU
============================================================

Ten dokument jest aktualnym planem strategicznym i stanem rozwoju
nowej Finory.

Najważniejsza zasada:

    STARA FINORA = LEGACY REFERENCE
    NOWA FINORA = WŁAŚCIWY PRODUKT

Stara aplikacja służy do poznania:
- funkcji,
- danych,
- reguł biznesowych,
- edge cases,
- istniejącego zachowania,
- historycznych ograniczeń.

Nie jest wzorcem implementacyjnym.

Nowa Finora jest budowana greenfield na docelowej architekturze.

Migracja starych danych jest osobnym etapem i nie może blokować
powstania pierwszego używalnego MVP.

============================================================
2. GŁÓWNY CEL PRODUKTU
============================================================

Finora ma docelowo być prywatną, lokalną, szybką aplikacją do
zarządzania finansami osobistymi.

Podstawowe założenia:

- local-first,
- IndexedDB jako podstawowe źródło danych,
- działanie offline,
- brak uzależnienia podstawowych funkcji od chmury,
- modularna architektura,
- kontrolowany application state,
- oddzielenie UI od storage,
- logika biznesowa niezależna od UI,
- silna izolacja danych użytkownika,
- backup i recovery,
- bezpieczeństwo jako wymaganie ciągłe,
- lokalna inteligencja przed zewnętrznym AI,
- AI jako opcjonalna warstwa,
- cloud jako opcjonalna warstwa,
- brak automatycznych przelewów/płatności przez AI na obecnym etapie.

Docelowo system może zostać rozszerzony o AI, automatyzację,
synchronizację oraz zarządzanie innymi usługami, ale nie jest to
warunek pierwszego MVP.

5. CO JUŻ FAKTYCZNIE DZIAŁA W NOWEJ ARCHITEKTURZE
============================================================

Nie oznacza to jeszcze, że użytkownik może korzystać z nowej Finory
jak z gotowej aplikacji.

Obecnie istnieją przede wszystkim fundamenty techniczne.

5.1 Storage

Zbudowano lokalny storage oparty o IndexedDB.

Główne założenia:
- baza "finora",
- storage key-value,
- bez uzależnienia od Firebase,
- transakcje aplikacyjne,
- bezpieczne commit/abort,
- ochrona przed problemami z równoległymi transakcjami,
- kopiowanie danych w pamięci,
- rzeczywista weryfikacja w Chromium.

5.2 Repositories

Zbudowano sześć repozytoriów:
- UserRepository,
- AccountRepository,
- CategoryRepository,
- TransactionRepository,
- BudgetRepository,
- GoalRepository.

Repozytoria zapewniają m.in.:
- zapis,
- odczyt,
- wyszukiwanie,
- filtrowanie,
- archiwizację,
- ownership isolation.

5.3 Persistence Composition

Istnieje composition root tworzący:
- storage,
- user repository,
- account repository,
- category repository,
- transaction repository,
- budget repository,
- goal repository.

Brak singletona i globalnego stanu.

5.4 Logika biznesowa

Istnieją przygotowane elementy logiki, m.in.:
- Safe-to-Spend,
- Budget Progress,
- Goal Required Deposit,
- Goal ETA,
- część wcześniejszych kalkulatorów i usług.

Sama obecność kalkulatora nie oznacza jeszcze gotowej funkcji UI.

5.5 Backup / Restore

Istnieje wcześniejszy fundament backup/restore:
- walidacja,
- integralność,
- preview,
- backup przed restore,
- rollback,
- ochrona ownership,
- obsługa wersji/schema.

Nie jest to jeszcze pełna, zintegrowana funkcja nowej aplikacji MVP.

7. NAJWAŻNIEJSZE REGUŁY DOMENY
============================================================

Account:
- cash / bank / savings w MVP,
- możliwość archiwizacji,
- ownership przez userId.

Transaction:
- amount dodatni,
- type = income | expense,
- categoryId może być null,
- data,
- opis,
- notes,
- controlled metadata,
- archiwizacja.

Opening balance:
- dodatni opening balance reprezentowany jako income,
- ujemny jako expense z wartością bezwzględną,
- opening balance wyłączony z normalnych metryk.

Category:
- income lub expense,
- MVP bez hierarchii,
- parentId = null,
- system roles dla wymaganych kategorii,
- archiwizacja.

Budget:
- monthly,
- powiązany z kategorią,
- archiwizacja,
- brak hard delete.

Goal:
- current jest rebuildable cache,
- źródłem prawdy są kwalifikujące transakcje goal contribution,
- brak automatycznego clampowania current,
- wpłata ponad target jest odrzucana,
- zmiany transakcji wymagają atomowej korekty current.

Safe-to-Spend MVP:
    safeTotal = spendable balances - goal requirements

daysLeft:
- deterministyczne,
- minimum 1.

Wszystkie te zasady są częścią zamrożonych kontraktów i architektury.

8. G1.2 — APPLICATION CONTRACTS
============================================================

Zamrożono dokładnie 31 operacji:
- 16 commands,
- 15 queries.

Najważniejsze zasady:
- getProfile rzuca NOT_FOUND, jeśli profil nie istnieje,
- błędne wejście używa VALIDATION_FAILED,
- storage failure może używać STORAGE_UNAVAILABLE,
- archiveBudget zamiast hard delete,
- transaction update nie archiwizuje,
- osobne archiveTransaction,
- Goal creation nie przyjmuje current,
- Goal.current zaczyna od 0,
- początkowe finansowanie przez depositToGoal,
- brak MVP-1 tags dla transakcji,
- Safe-to-Spend jest niezależny od legacy/global state.

Frozen API nie może być zmieniane bez konkretnego blokera.

26. BRAMKI JAKOŚCI

[ ] jasno określonego zakresu
[ ] implementacji
[ ] testów
[ ] hostile audit

Critical / High:
    zawsze blokują.

Medium:
    domyślnie blokują, chyba że istnieje konkretna, uzasadniona decyzja
    o świadomym odłożeniu problemu.

Low:
    może zostać zaakceptowany, jeśli:
    - nie zagraża architekturze,
    - nie zagraża danym,
    - nie tworzy istotnego długu,
    - jest zapisany do backlogu.

============================================================
30. DEFINICJA SUKCESU MVP
============================================================

MVP jest gotowe, gdy użytkownik może:

1. wejść do nowej Finory,
2. utworzyć swój profil,
3. dodać konta,
4. ustawić salda początkowe,
5. dodawać przychody,
6. dodawać wydatki,
7. kategoryzować transakcje,
8. przeglądać historię,
9. poprawiać/archiwizować transakcje,
10. tworzyć budżety,
11. sprawdzać wykonanie budżetów,
12. tworzyć cele,
13. finansować cele,
14. sprawdzać postęp celów,
15. korzystać z Safe-to-Spend,
16. oglądać podstawowe statystyki,
17. korzystać z dashboardu,
18. pracować offline,
19. mieć dane zapisane lokalnie,
20. wykonać podstawowe bezpieczne backup/restore.

MVP nie musi jeszcze posiadać:
- migracji starej Finory,
- AI,
- chmury,
- inwestycji,
- zaawansowanych automatyzacji,
- wszystkich funkcji legacy.

============================================================
31. ZASADA KOŃCOWA
============================================================

Najważniejsza zasada całego projektu:

    STARA FINORA JEST ŹRÓDŁEM WIEDZY.
    NOWA FINORA JEST WŁAŚCIWYM PRODUKTEM.

Nie musimy ratować starej architektury.
Nie musimy przepisywać starego kodu linia po linii.
Nie musimy usuwać każdej starej zmiennej.

Musimy wykorzystać wiedzę zdobytą podczas discovery i zbudować
lepszy, prostszy, bezpieczniejszy i bardziej skalowalny system.

Drugą zasadą jest:

    SZYBCIEJ, ALE NIE BYLE JAK.

Każdy etap ma być możliwie mały i szybki, ale końcowy kod ma być
przetestowany, zweryfikowany i odporny na hostile audit.

============================================================
32. AKTUALNY STAN W JEDNYM ZDANIU
============================================================

Finora ma już solidne, zweryfikowane fundamenty domeny, kontraktów,
storage, repozytoriów i persistence; obecnie kończymy pierwszy moduł
aplikacyjny, a następnie przechodzimy przez Application Modules,
State i UI, aby możliwie szybko doprowadzić do pierwszego naprawdę
używalnego MVP — bez poświęcania jakości, bezpieczeństwa i testów.
