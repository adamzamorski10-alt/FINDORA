## 1. Product Principles

1. **Local-first**: All data lives on the user's device. Cloud sync is optional, not required.
2. **Privacy by design**: Sensitive financial data stays local. No telemetry, no ads, no third-party sharing.
3. **Financial correctness**: Calculations are deterministic, tested, and auditable. No rounding surprises.
4. **Simple data model**: Clear entity boundaries. No flat transactions with 20+ underscore flags.
5. **Offline capability**: Core features work without network.
6. **Extensible architecture**: New modules (Giełda, Resale, etc.) can be added as plugins without changing core.
7. **No Firebase dependency**: Storage-agnostic core. Firebase/Mock adapters are implementation details.
8. **No global state**: Proper state management with explicit data flow.
9. **Polish market awareness**: Built-in support for PLN, Polish categories, and common Polish financial instruments (PPK, IKZE, etc.) where relevant.

## 2. CORE

Features that must ship in the first usable version (MVP-1). Without these, the product is not a personal finance manager.

### 2.1 Transactions
**Why CORE**: The fundamental unit of financial tracking. Every other feature depends on it.
**Scope**: Income and expense entries with amount, category, date, description, and account. No transfers in MVP-1 (see REDESIGN).
**Dependencies**: Accounts → Categories → Balances.

### 2.2 Accounts / Money Places
**Why CORE**: Users need to know where their money is. Without accounts, transactions are meaningless.
**Scope**: Named accounts with optional icon/color. Support for `konto`, `skarbonka`, and custom accounts. `gielda` is dropped from money places (see REDESIGN).
**Dependencies**: None (foundational).

### 2.3 Categories
**Why CORE**: Essential for organizing expenses and understanding spending patterns.
**Scope**: Predefined expense categories (food, transport, housing, etc.) with icons and colors. Custom categories allowed. Income categories optional in MVP-1.
**Dependencies**: None.

### 2.4 Balances
**Why CORE**: Users need to see current account balances. This is the primary "what do I have" view.
**Scope**: Per-account balance computed from transactions. Historical balance (as-of date) is NEXT.
**Dependencies**: Transactions, Accounts.

### 2.5 Budgets
**Why CORE**: Budgeting is a primary reason users adopt finance apps. Without it, the app is just a ledger.
**Scope**: Monthly spending limits per category. Progress visualization. Over-budget alerts.
**Dependencies**: Categories, Transactions, Balances.

### 2.6 Goals
**Why CORE**: Savings goals are a core motivator. Simple target-based goals with progress tracking.
**Scope**: Name, target amount, current amount, deadline, optional icon. Manual deposits only in MVP-1 (no auto-save).
**Dependencies**: Accounts (for deposits), Transactions.

### 2.7 Basic Reports
**Why CORE**: Users need to understand their financial behavior. Without reports, data is opaque.
**Scope**: Monthly income/expense summary, category breakdown, simple trend (last 3-6 months).
**Dependencies**: Transactions, Categories, Accounts.

### 2.8 Safe-to-Spend
**Why CORE**: Unique and valuable feature from legacy. Gives users a daily budget based on remaining funds, bills, and goals.
**Scope**: Daily safe-to-spend amount. Includes upcoming bills and goal requirements.
**Dependencies**: Balances, Recurring Transactions (for bills), Goals.

### 2.9 Data Persistence
**Why CORE**: No app is usable without saving data.
**Scope**: Local-first storage (SQLite/IndexedDB). Export to JSON/CSV. No cloud sync in MVP-1.
**Dependencies**: All entities.

## 3. NEXT

Important features to build immediately after CORE (MVP-2 and early V1). They add significant value but don't block initial release.

### 3.1 Recurring Transactions
**Why NEXT**: Bills and subscriptions are a major part of personal finance. Safe-to-Spend depends on them.
**Scope**: Active/inactive rules with frequency (weekly/monthly/yearly), next date projection, booking. No subscriptions special handling in NEXT.
**Dependencies**: Transactions, Categories, Accounts.

### 3.2 Auto-Save Rules
**Why NEXT**: Automates savings behavior. Valuable but not blocking.
**Scope**: Percentage-based savings from income to a goal or account. Round-up savings from expenses.
**Dependencies**: Transactions, Goals, Accounts.

### 3.3 Tags & Notes
**Why NEXT**: Adds context to transactions without forcing rigid categorization.
**Scope**: Free-text tags (multi-value) and notes on transactions. Searchable/filterable.
**Dependencies**: Transactions.

### 3.4 Net Worth
**Why NEXT**: Gives a complete financial picture. Not blocking for daily use.
**Scope**: Sum of all account balances + liabilities (if debt tracking exists). Monthly snapshots.
**Dependencies**: Accounts, Balances, (optional) Debtors/Creditors.

### 3.5 Advanced Reports
**Why NEXT**: Power users need deeper insights. Can be added after basic reports are stable.
**Scope**: Category ranking, monthly trends, year-over-year comparison, anomaly detection.
**Dependencies**: Transactions, Categories, Basic Reports.

### 3.6 Data Import/Export
**Why NEXT**: Users need to migrate data. Export is essential for backup. Import is needed for onboarding from other apps.
**Scope**: JSON export/import. CSV export. No Vinted/scraper integration.
**Dependencies**: All entities.

### 3.7 Backup & Restore
**Why NEXT**: Local-first means users need to back up their own data.
**Scope**: Encrypted backup file (JSON + AES). Restore from backup. No cloud backup in NEXT.
**Dependencies**: Data Persistence.

### 3.8 Privacy Mode
**Why NEXT**: Hides amounts in the UI. Simple toggle, persisted locally.
**Scope**: Mask all monetary values with `•••`. No password protection (that's NEXT+).
**Dependencies**: None (UI layer).

### 3.9 Theme
**Why NEXT**: Dark mode and system theme support. Expected in modern apps.
**Scope**: Light/dark/system theme. Persisted preference.
**Dependencies**: None (UI layer).

## 4. OPTIONAL

Valuable features that can wait until V1 or later without blocking the core product.

### 4.1 Debtors
**Why OPTIONAL**: Useful for tracking IOUs but not essential for personal finance. Many users never use it.
**Scope**: Simple debt tracking with repayment history.
**Dependencies**: Transactions, Accounts.

### 4.2 Creditors / Loans
**Why OPTIONAL**: Similar to debtors. Useful for tracking borrowed money but not core.
**Scope**: Loan tracking with repayment schedule. Interest display only (not used in calculations).
**Dependencies**: Transactions, Accounts.

### 4.3 Giełda (Stock Market)
**Why OPTIONAL**: Niche feature for users who track investments. Complex because it needs separate P&L logic.
**Scope**: Deposits, withdrawals, earnings, losses. Balance calculation. Separate from main accounts.
**Dependencies**: Accounts (for deposits/withdrawals), Transactions.

### 4.4 Strony (Service Business)
**Why OPTIONAL**: Very specific to Polish freelancers/service providers. Not general personal finance.
**Scope**: Products, clients, sales pipeline. Auto-income from sold clients.
**Dependencies**: Transactions, Accounts, Income Sources.

### 4.5 Resale (E-commerce)
**Why OPTIONAL**: Complex and specific to resellers. High implementation cost.
**Scope**: Products, sales, shipments, tasks. Internal wallet. 48h shipping deadline.
**Dependencies**: Transactions, Accounts, Income Sources, Products.

### 4.6 Reminders
**Why OPTIONAL**: Nice-to-have but not blocking. Can be implemented as OS-level notifications.
**Scope**: Bill reminders, task reminders. Local notifications only.
**Dependencies**: None.

### 4.7 Global Search
**Why OPTIONAL**: Useful for large datasets but not essential for MVP.
**Scope**: Full-text search across transactions, descriptions, notes.
**Dependencies**: Transactions, Tags/Notes.

### 4.8 Vinted Integration
**Why OPTIONAL**: Very niche. Legacy implementation is localStorage-based and fragile.
**Scope**: Price tracking for Vinted items. Scraper integration.
**Dependencies**: Resale.

## 5. REDESIGN

Features that are valuable but need complete redesign for the greenfield product. The legacy implementation is too coupled to global state, flat schemas, or Firebase.

### 5.1 Dashboard / Layouts
**Why REDESIGN**: Legacy uses SortableJS drag-and-drop with complex state management. In greenfield, use a simpler widget system with declarative layouts. No need for real-time Firebase sync of layout state.
**New approach**: JSON schema for widget configuration. Local-first. Optional cloud sync.

### 5.2 Transfers
**Why REDESIGN**: Legacy simulates transfers as paired transactions with `_transfer` flag. This creates balance calculation inconsistencies.
**New approach**: First-class `Transfer` entity with `fromAccount`, `toAccount`, `amount`, `date`, `fee`. Excluded from income/expense totals. Clear audit trail.

### 5.3 Auto-Save Rules
**Why REDESIGN**: Legacy has two overlapping mechanisms (rules + goal round-up). Complex and hard to reason about.
**New approach**: Unified "Savings Rules" engine. Rule = trigger (income received, expense made, date) → action (move to goal, move to account, round up). Declarative and testable.

### 5.4 Guest Mode
**Why REDESIGN**: Legacy implementation is complex (guest links, debtor-specific sharing, nicknames). In greenfield, if sharing is needed, use a simple read-only share link or export. Full guest mode is OUT OF SCOORE for V1.
**New approach**: Drop in MVP-1. Re-evaluate as "Shared Budgets" in V1+ if needed.

### 5.5 Resale
**Why REDESIGN**: Legacy is very specific to Polish resale workflow (Vinted, Allegro, OLX). Complex status machine, internal wallet, shipment tracking, labels.
**New approach**: If kept, should be a plugin module with clean separation from core finance. Simplify status machine. External storage for labels. No internal wallet unless proven essential.

### 5.6 Strony
**Why REDESIGN**: Legacy is tightly coupled to service business workflow. Complex import logic, client pipeline, auto-income.
**New approach**: If kept, should be a plugin module. Simplify to "Projects" or "Income Sources" with basic tracking. Drop auto-income in favor of explicit transactions.

### 5.7 Giełda
**Why REDESIGN**: Legacy treats it as both a money place and an income source. Confusing dual nature.
**New approach**: Separate "Investments" module. Not a money place. Track positions, transactions, dividends separately. Balance is portfolio value, not cash.

### 5.8 Income Model (Sources + Profiles)
**Why REDESIGN**: Legacy has dual model (`incomeSources` array + `incomeProfiles` object map). Inconsistent and confusing.
**New approach**: Single "Income Sources" entity with optional grouping (profiles). Clean foreign keys.

## 6. DROP

Features that should NOT be migrated to the new Finora. They are either legacy artifacts, too niche, or replaced by better alternatives.

### 6.1 Vinted Price Tracker
**Reason**: localStorage-based, fragile, very niche. Not core to personal finance. Can be a separate browser extension.

### 6.2 Guest Mode (legacy implementation)
**Reason**: Too complex, security risks, not core. Replace with simple export/share in V1+.

### 6.3 Global State Architecture
**Reason**: Technical debt. Replace with proper state management.

### 6.4 Inline Base64 Label Storage
**Reason**: `_labelData` in resaleSales bloats the database. Use external file storage or drop.

### 6.5 `isSubscription` Flag
**Reason**: Defined but never meaningfully used. Recurring rules already cover subscriptions.

### 6.6 `_stripUndefinedDeep` Legacy Boundary
**Reason**: Inconsistent persistence. Use explicit schema validation instead.

### 6.7 `uid()` Generator
**Reason**: `Date.now().toString(36) + random` is collision-prone. Use UUID v4 or ULID.

### 6.8 `RESALE_EVENTS_MAX = 5000` Hard Cap
**Reason**: Arbitrary limit without archiving strategy. Use proper event sourcing or drop events if not needed.

### 6.9 `activeMoneyPlace` Global
**Reason**: Legacy UI state. In greenfield, use proper view routing.

### 6.10 `_vintedPrices` / `_vintedMeta`
**Reason**: Unused in core flows. Drop with Vinted integration.

## 7. UNCERTAIN

Features that need a product decision before categorization. Do NOT implement without clarification.

### 7.1 Debtors
**Uncertainty**: Is debt tracking core for Polish users? Or is it optional? Many personal finance apps omit it.
**Recommendation**: Start as OPTIONAL. Re-evaluate based on user feedback.

### 7.2 Creditors / Loans
**Uncertainty**: Same as debtors. Also, interest calculation is display-only in legacy. Should we support amortization schedules?
**Recommendation**: Start as OPTIONAL with simple tracking. Add interest calculation in V1+.

### 7.3 Giełda
**Uncertainty**: How many users actually use it? Is it worth the complexity? Should it be a separate module or integrated?
**Recommendation**: Start as OPTIONAL plugin. Validate usage before investing in REDESIGN.

### 7.4 Strony
**Uncertainty**: Is this a personal finance feature or a business CRM? The boundary is blurry.
**Recommendation**: Start as OPTIONAL plugin. If usage is low, consider DROP.

### 7.5 Resale
**Uncertainty**: High complexity vs. unclear user value. Many features (shipments, labels, 48h deadlines) are very specific.
**Recommendation**: Start as OPTIONAL plugin with simplified workflow. Drop advanced features (labels, shipments) unless requested.

### 7.6 Reminders
**Uncertainty**: OS-level notifications may suffice. Is a custom reminder system needed?
**Recommendation**: Start as OPTIONAL. Use platform notifications if possible.

### 7.7 Privacy Mode
**Uncertainty**: Is masking amounts sufficient, or do users need full encryption/password protection?
**Recommendation**: Start with simple masking (NEXT). Add password protection in V1+.

### 7.8 Cloud Sync
**Uncertainty**: Not in MVP, but should it be a paid feature? What's the sync strategy (CRDT, last-write-wins)?
**Recommendation**: Decision needed before V1. Likely OPTIONAL/V1+.

## 8. MVP-1

**Goal**: Smallest useful personal finance manager. Users can track accounts, record transactions, set budgets, and see basic reports.

### Included
| Feature | Scope |
|---|---|
| Accounts | Create/edit/delete accounts. Default: `konto`, `skarbonka`. |
| Transactions | Add/edit/delete income/expense. Amount, category, date, description. |
| Categories | Predefined + custom. Icons and colors. |
| Balances | Current balance per account. |
| Budgets | Monthly limits per category. Progress ring. Over-budget indicator. |
| Goals | Name, target, current, deadline. Manual deposits. |
| Reports | Monthly income/expense, category breakdown, 3-month trend. |
| Safe-to-Spend | Daily amount based on balance, bills, goals. |
| Data Persistence | Local SQLite/IndexedDB. JSON export. |

### Not Included (deferred to NEXT or later)
- Recurring transactions (manual entry only)
- Auto-save rules
- Tags/notes
- Net worth
- Advanced reports (anomalies, YoY, rankings)
- Transfers (use paired transactions in MVP-1, redesign later)
- Debtors, creditors, loans
- Giełda, Strony, Resale
- Reminders
- Privacy mode
- Theme
- Backup/restore
- Import
- Global search
- Dashboard customization

### Dependencies in MVP-1
```
Accounts → Transactions → Balances → Safe-to-Spend
Categories → Transactions → Budgets → Reports
Goals → Safe-to-Spend
```

## 13. Recommended Build Order

### Phase 1: Foundation (MVP-1)
1. **Data Layer**: Local-first storage, schema, migrations
2. **Accounts**: CRUD, basic validation
3. **Categories**: Predefined + custom
4. **Transactions**: CRUD, filtering by month/account/category
5. **Balances**: Real-time per-account
6. **Budgets**: Monthly limits, progress
7. **Goals**: Basic target tracking
8. **Reports**: Monthly summary, category breakdown
9. **Safe-to-Spend**: With recurring bills
10. **Recurring Transactions**: For bills and subscriptions
11. **Export**: JSON/CSV

### Phase 2: Automation (MVP-2)
12. **Auto-Save Rules**: Percentage and round-up
13. **Tags & Notes**: On transactions
14. **Privacy Mode**: Masking
15. **Import**: JSON import
16. **Backup & Restore**: Encrypted backup
17. **Theme**: Dark/light/system

### Phase 3: Advanced (V1)
18. **Transfers (REDESIGN)**: First-class entity
19. **Net Worth**: Assets - liabilities
20. **Advanced Reports**: Anomalies, YoY, rankings
21. **Debtors/Creditors**: Basic tracking
22. **Giełda**: Basic P&L (if approved)
23. **Reminders**: Local notifications
24. **Global Search**: Full-text
25. **Cloud Sync**: Optional, encrypted

### Phase 4: Plugins (Later)
26. **Strony**: Evaluate and build if justified
27. **Resale**: Evaluate and build if justified
28. **Vinted Integration**: Separate from core
29. **AI Insights**: ML-based suggestions

These decisions cannot be made by the engineering team alone. They require product strategy input.

| # | Decision | Options | Impact |
|---|---|---|---|
| 1 | **Debtors/Creditors** | Core, Optional, or Drop? | Affects 20% of legacy features. Core expands scope significantly. |

| 5 | **Cloud Sync** | Free or paid? E2E encrypted or not? | Affects architecture, pricing, legal. |
| 6 | **Bank Integration** | Never, V1+, or Later? | High effort, high value, but requires compliance. |
| 7 | **Privacy Mode** | Masking only or full encryption/password? | Affects UX and security model. |
| 8 | **AI Features** | None in V1, or basic insights? | Requires data aggregation and ML pipeline. |
| 9 | **Multi-currency** | PLN only or multi-currency? | Affects all monetary calculations. |
| 10 | **Shared Budgets** | Replace Guest Mode or skip? | Requires multi-user sync and permissions. |

## Summary

The greenfield Finora should focus on **core personal finance** with a clean, local-first architecture. The legacy app has many valuable features, but also significant technical debt and niche functionality. The recommended approach is:

1. **MVP-1**: Rock-solid core (accounts, transactions, budgets, goals, basic reports).
2. **MVP-2**: Automation (recurring, auto-save, tags).
3. **V1**: Advanced features (transfers, net worth, debt/loan, basic Giełda).
4. **Later**: Niche modules (Strony, Resale, Vinted) and cloud features.

**Key principle**: Build a great personal finance app first. Add niche features later as plugins if there's user demand.
