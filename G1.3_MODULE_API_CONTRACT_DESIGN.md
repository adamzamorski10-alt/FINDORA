## 1. SOURCE-OF-TRUTH HIERARCHY

This document defines the module/API architecture required to implement the frozen baseline. It does not redefine business rules.

**G1.1** — Domain entities, invariants, business rules, derived-value definitions, lifecycle semantics, source-of-truth rules.

**G1.2** — Application commands/queries, service contracts, validation, ownership, error contracts, persistence effects.

**G1.3** — Module boundaries, responsibility boundaries, dependency direction, repository interfaces, calculator boundaries, application orchestration, atomicity boundary, composition root, UI boundary, and mapping of G1.2 operations to modules.

G1.3 MUST NOT redefine or silently alter G1.1 or G1.2. Where G1.3 references a G1.1/G1.2 rule, it references that rule rather than creating a second independent version.

## 3. MODULE RESPONSIBILITIES

### 3.1 UserModule

**Responsibility**: Provide access to the current user's profile.

**G1.2 operations**: `getProfile`

**Dependencies**: `UserRepository`

**Prohibited**: No direct storage access, no business logic, no orchestration.

---

### 3.2 AccountModule

**Responsibility**: Account lifecycle, including atomic creation with opening-balance transaction.

**G1.2 operations**: `createAccount`, `getAccount`, `getActiveAccounts`, `updateAccount`, `archiveAccount`

**Dependencies**: `AccountRepository`, `TransactionRepository`

**Prohibited**: No direct StorageAdapter access.

**Cross-entity orchestration**: `createAccount` must create the account and opening-balance transaction atomically within an ApplicationTransaction boundary.

---

### 3.3 CategoryModule

**Responsibility**: Category lifecycle, including protection against archiving categories referenced by active budgets.

**G1.2 operations**: `createCategory`, `getSystemCategories`, `archiveCategory`

**Dependencies**: `CategoryRepository`, `BudgetRepository`

**Prohibited**: No direct StorageAdapter access.

**Cross-entity orchestration**: `archiveCategory` must reject archiving if active budgets reference the category.

---

### 3.4 TransactionModule

**Responsibility**: Transaction lifecycle, validation, archival, and atomic goal-current adjustment signaling.

**G1.2 operations**: `createTransaction`, `updateTransaction`, `archiveTransaction`, `getTransactionsByMonth`, `getTransactionsByAccount`

**Dependencies**: `TransactionRepository`, `IGoalCurrentAdjuster` (one-way interface to GoalModule)

**Prohibited**: No direct `GoalRepository.save()` for Goal.current updates. No direct StorageAdapter access. No dependency on GoalModule implementation.

**Cross-entity orchestration**: When a transaction with `metadata.goalId` is created, updated, or archived, TransactionModule invokes `IGoalCurrentAdjuster.adjust(goalId, delta)` within the same ApplicationTransaction boundary.

---

### 3.5 BudgetModule

**Responsibility**: Budget lifecycle and progress calculation.

**G1.2 operations**: `createBudget`, `getBudgetProgress`, `updateBudget`, `archiveBudget`

**Dependencies**: `BudgetRepository`, `TransactionRepository`, `CategoryRepository`

**Prohibited**: No direct StorageAdapter access.

---

### 3.6 GoalModule

**Responsibility**: Goal lifecycle, Goal.current invariant, atomic deposit/current updates, rebuild, ETA.

**G1.2 operations**: `createGoal`, `updateGoal`, `depositToGoal`, `archiveGoal`, `rebuildGoalCurrent`, `getActiveGoals`, `getGoalEta`, `getRequiredDepositsThisMonth`

**Dependencies**: `GoalRepository`, `TransactionRepository`, `CategoryRepository`

**Prohibited**: No direct StorageAdapter access. No dependency on TransactionModule.

**Cross-entity orchestration**: GoalModule owns the Goal.current invariant. It is the sole module authorized to persist Goal.current changes. Transaction-triggered changes arrive via `IGoalCurrentAdjuster` interface.

---

### 3.7 SafeToSpendModule

**Responsibility**: Safe-to-Spend calculation orchestration.

**G1.2 operations**: `computeSafeToSpend`, `computeForCurrentState`

**Dependencies**: `SafeToSpendCalculator`, `AccountRepository`, `GoalRepository`, `TransactionRepository`

**Prohibited**: No global state, no `dbData`, no Firebase, no StorageAdapter access.

**Cross-entity orchestration**: SafeToSpendModule obtains goal data from GoalRepository, computes required monthly deposits via GoalRequiredDepositCalculator, derives freeFunds from AccountRepository and TransactionRepository, and computes the final Safe-to-Spend result via SafeToSpendCalculator with explicit inputs. No bills in MVP-1.

---

### 3.8 ReportingModule

**Responsibility**: Read-model aggregation for reports.

**G1.2 operations**: `getMonthlySummary`, `getMonthCategoryBreakdown`, `getAccountBalance`

**Dependencies**: `TransactionRepository`, `AccountRepository`, `CategoryRepository`

**Prohibited**: No direct StorageAdapter access. No persistence. No mutation.

## 5. GOAL.CURRENT OWNERSHIP

**Single authoritative owner**: GoalModule owns the Goal.current invariant, calculation logic, and all mutations.

**Invariant** (from G1.1): `Goal.current = sum of all non-archived qualifying goal-contribution transactions`

**Transaction-triggered changes**: When TransactionModule processes a transaction that affects Goal.current (create, update, archive with `metadata.goalId`), it MUST NOT call GoalRepository.save() directly for Goal.current updates. Instead:

1. TransactionModule invokes `IGoalCurrentAdjuster.adjust(goalId, delta)` within the ApplicationTransaction boundary.
2. GoalModule receives the adjustment, recalculates `current` from the full qualifying transaction set, and persists via `GoalRepository.save()`.
3. Goal.current logic remains in one place: GoalModule.

**No circular dependency**: GoalModule does not depend on TransactionModule. TransactionModule depends on `IGoalCurrentAdjuster` interface only. GoalModule reads transactions via `TransactionRepository` when needed for rebuilds. The dependency graph remains acyclic.

**No second source of truth**: Only GoalModule computes and persists Goal.current. TransactionModule merely signals that a qualifying transaction changed.

**Rebuild path**: `rebuildGoalCurrent` is owned by GoalModule. It reads all transactions via `TransactionRepository`, recalculates the exact sum, and persists atomically.

## 6. ATOMICITY / APPLICATION TRANSACTION

### 6.1 ApplicationTransaction Boundary

G1.3 defines an **ApplicationTransaction** abstraction at the application module layer. This abstraction:

- Spans multiple repository calls required by a single G1.2 command.
- Ensures all persistence succeeds or fails together.
- Is provided by infrastructure.
- Is consumed by application modules.
- Does NOT allow partial persistence.

Repositories themselves remain entity-scoped. They do not coordinate with each other. Partial persistence is forbidden at the application layer.

The concrete persistence transaction mechanism (e.g., IndexedDB transaction, compensating writes, etc.) is NOT defined in G1.3. **G3 — Local Storage Foundation** defines the concrete mechanism.

### 6.2 Commands Requiring Atomic Multi-Repository Persistence

The following G1.2 commands MUST execute within a single ApplicationTransaction boundary:

| G1.2 Command | Repositories Involved |
|---|---|
| `createAccount` | AccountRepository + TransactionRepository (opening balance) |
| `createTransaction` (goal contribution) | TransactionRepository + GoalRepository (via GoalModule/IGoalCurrentAdjuster) |
| `updateTransaction` (goal contribution correction) | TransactionRepository + GoalRepository (via GoalModule/IGoalCurrentAdjuster) |
| `archiveTransaction` (goal contribution) | TransactionRepository + GoalRepository (via GoalModule/IGoalCurrentAdjuster) |
| `depositToGoal` | TransactionRepository + GoalRepository |

**Note on `rebuildGoalCurrent`**: This command reads transaction data from `TransactionRepository` and performs a single `GoalRepository.save()` write. It is atomic at the repository level (single write replaces `Goal.current`), but it does NOT require multi-repository rollback coordination because only one repository persists state.

### 6.3 Atomicity Guarantee

For commands listed above:

- All required repository writes must commit atomically.
- If any repository write fails, all prior writes within the boundary must be rolled back before the error propagates.
- G1.3 does not specify the rollback mechanism. G3 — Local Storage Foundation provides it.
- Single-repository commands (e.g., `archiveGoal`, `updateBudget`, `rebuildGoalCurrent`) are atomic at the repository level and do not require ApplicationTransaction coordination.

## 7. REPOSITORY BOUNDARIES

Repositories are architectural boundaries, not concrete storage implementations.

### 7.1 Common Repository Rules

All MVP-1 repositories MUST:

- Expose lifecycle operations that match the entity lifecycle defined by frozen G1.1/G1.2.
- Enforce user ownership filtering on all operations.
- Expose archive for entities for which archive semantics are defined; entities without archive semantics (e.g., UserProfile) expose only the lifecycle operations required by G1.2.
- Never expose hard-delete entity lifecycle.
- Return explicit storage failures (STORAGE_UNAVAILABLE) rather than masking them.
- Never depend on application modules, calculators, UI, or StorageAdapter details.
- Accept a StorageAdapter instance in construction.

### 7.2 UserRepository

```javascript
interface UserRepository {
  findById(id: string): Promise<UserProfile | null>
  save(entity: UserProfile): Promise<void>
}
```

### 7.3 AccountRepository

```javascript
interface AccountRepository {
  loadAll(): Promise<Account[]>
  findById(id: string): Promise<Account | null>
  save(entity: Account): Promise<void>
  archive(id: string): Promise<void>
}
```

### 7.4 CategoryRepository

```javascript
interface CategoryRepository {
  loadAll(): Promise<Category[]>
  findById(id: string): Promise<Category | null>
  findSystem(): Promise<Category[]>
  save(entity: Category): Promise<void>
  archive(id: string): Promise<void>
}
```

### 7.5 TransactionRepository

```javascript
interface TransactionRepository {
  loadAll(): Promise<Transaction[]>
  findById(id: string): Promise<Transaction | null>
  findByMonth(monthKey: string): Promise<Transaction[]>
  findByAccount(accountId: string): Promise<Transaction[]>
  save(entity: Transaction): Promise<void>
  archive(id: string): Promise<void>
}
```

### 7.6 BudgetRepository

```javascript
interface BudgetRepository {
  findAll(): Promise<Budget[]>
  findById(id: string): Promise<Budget | null>
  findByCategory(categoryId: string): Promise<Budget | null>
  save(entity: Budget): Promise<void>
  archive(id: string): Promise<void>

```

### 7.7 GoalRepository

```javascript
interface GoalRepository {
  loadAll(): Promise<Goal[]>
  findById(id: string): Promise<Goal | null>
  save(entity: Goal): Promise<void>
  archive(id: string): Promise<void>
}
```

### 7.8 Repository Omissions

G1.3 does NOT define repositories for entities not in the MVP-1 entity set: RecurringRule, Transfer, SavingsRule, Person, InvestmentAccount, Product, Sale, Event.

G1.3 does NOT include reactive listener methods, batch persistence methods, or category/account/user-specific bulk query methods beyond what is required by frozen G1.2 operations.

## 8. STORAGE ADAPTER BOUNDARY

### 8.1 Interface

```javascript
interface StorageAdapter {
  get(key: string): Promise<any>
  set(key: string, value: any): Promise<void>
  update(key: string, updater: (value: any) => any): Promise<void>
  remove(key: string): Promise<void>
}
```

### 8.2 Rules

- Repositories depend on StorageAdapter.
- Application modules do NOT depend on StorageAdapter.
- UI does NOT depend on StorageAdapter.
- Concrete implementations belong to **G3 — Local Storage Foundation**.
- If StorageAdapter exposes low-level `remove()`, this is physical storage cleanup only. Entity lifecycle semantics at the repository/application layer remain archive-only. Physical removal MUST NOT violate domain lifecycle rules.

### 8.3 Prohibited

G1.3 does NOT define:
- Concrete IndexedDB object stores
- Storage keys
- Serialization formats
- Indexes
- Migrations
- Database schema details

## 9. CALCULATOR BOUNDARIES

Calculators are pure deterministic functions with explicit inputs and outputs.

### 9.1 SafeToSpendCalculator

**Responsibility**: Compute Safe-to-Spend values from explicit financial inputs.

**Inputs**: `{ freeFunds: number, goalsReq: number, daysLeft: number }`

**Output**: `{ safeTotal: number, perDay: number }`

**Consumed by**: SafeToSpendModule

**Rules**:
- `daysLeft` is clamped to `Math.max(1, daysLeft)` internally.
- `perDay` is always finite.
- `safeTotal` can be negative.

**G1.2 alignment**: Output shape and clamping behavior are governed by G1.2 §10.1. G1.3 does not redefine them.

---

### 9.2 BudgetProgressCalculator

**Responsibility**: Compute budget utilization from spent amount and limit.

**Inputs**: `{ budgetAmount: number, spent: number }`

**Output**: `{ progress: number, remaining: number, overBudget: boolean }`

**Consumed by**: BudgetModule

---

### 9.3 GoalRequiredDepositCalculator

**Responsibility**: Compute required monthly goal deposits.

**Inputs**: `{ goals: Goal[], currentDate: Date }`

**Output**: `number` — sum of `ceil((target - current) / monthsLeft)` for goals with deadline and remaining > 0.

**Consumed by**: GoalModule, SafeToSpendModule

**Rules**:
- `monthsLeft` is at least 1.
- Past deadline: entire remaining amount is added in full.

---

### 9.4 GoalEtaCalculator

**Responsibility**: Estimate goal completion date.

**Inputs**: `{ goal: Goal, monthlySavings: number }`

**Output**: `{ eta: string | null, monthsRemaining: number | null, requiredMonthly: number }`

**Consumed by**: GoalModule

---

### 9.5 Calculator Prohibitions

Calculators MUST NOT:
- Access repositories
- Access StorageAdapter
- Access global state
- Access UI
- Perform persistence
- Orchestrate application operations

## 10. DEPENDENCY DIRECTION

```
UI Layer
  ↓ calls public interfaces
Application Modules (8)
  ↓ use
Repository Interfaces (6) / Pure Calculators (4)
  ↓ depend on
StorageAdapter (interface)
  ↓ implemented by
Local Storage Adapter (MVP-1, defined in G3)
```

### 10.1 Allowed Dependencies

- Application Modules → Repositories
- Application Modules → Pure Calculators
- Application Modules → `IGoalCurrentAdjuster` interface (one-way, TransactionModule → GoalModule boundary)
- Repositories → StorageAdapter
- AppKernel → all of the above

### 10.2 Prohibited Dependencies

- Calculators → Repositories, StorageAdapter, UI
- Repositories → Application Modules, Calculators, UI
- Application Modules → StorageAdapter (must go through repositories)
- Application Modules → other Application Modules (except the one-way `IGoalCurrentAdjuster`)
- UI → Repositories, Calculators, StorageAdapter, AppKernel internals
- Any module → global state, `dbData`, Firebase, legacy globals

## 11. COMPOSITION ROOT

### 11.1 AppKernel

**Responsibility**: Instantiate and wire all modules.

**Owns**:
- StorageAdapter instantiation
- Repository instantiation with user ownership
- Calculator instantiation
- Application module instantiation with dependency injection
- Exposing a single UI-facing boundary: `AppKernel.modules`

**Must NOT own**:
- Business rules
- Validation logic
- Formulas
- Error messages
- Entity-specific orchestration
- UI components

## 12. UI BOUNDARY

The UI communicates exclusively through application module public interfaces:

```
UI → AppKernel.modules.<ModuleName>.<publicMethod>()
```

The UI MUST NOT:
- Call repositories directly
- Call calculators directly
- Access StorageAdapter
- Import IndexedDB modules
- Read/write `localStorage` directly
- Access global state
- Maintain a second authoritative financial state

UI obtains data through application queries/contracts. A future reactive mechanism MAY be designed in a later stage if concrete requirements justify it.

## 13. SOURCE-OF-TRUTH BOUNDARIES

| Value | Authoritative Source | Not Stored In |
|---|---|---|
| Account balance | Sum of non-archived Transactions for account | Account entity |
| Goal.current | Sum of qualifying goal-contribution Transactions (G1.1 invariant) | Goal entity (persisted rebuildable cache; authoritative source is the transaction set) |
| Budget progress | Sum of Transactions for budget category/period, excluding archived, opening-balance, and goal-contribution transactions | Budget entity |
| Safe-to-Spend | Computed from account balances and goal requirements | Not persisted |
| Monthly income/expense | Computed from Transactions | Not persisted |
| Category breakdown | Computed from Transactions | Not persisted |
| Goal ETA | Computed from Goal + transaction history | Not persisted |

**Second source of truth is prohibited.** All derived values must be recomputable from their authoritative sources as defined by G1.1.

## 14. FUTURE EXTENSION POINTS

Future modules attach at the **Application Module** layer without modifying core repositories or calculators.

| Future Feature | Extension Point | Core Impact |
|---|---|---|
| Transfers (V1+) | New `TransferModule` + `TransferRepository` | None |
| RecurringRules (MVP-2) | New `RecurringModule` + `RecurringRuleRepository` | None |
| SavingsRules (MVP-2) | New `SavingsModule` + `SavingsRuleRepository` | None |
| Tags (MVP-2) | Extend `TransactionModule` via explicit future design stage | None |
| Investments (V1+) | New `InvestmentModule` + `InvestmentAccountRepository` | None |
| Debt/Creditor (V1+) | New `DebtModule` + `PersonRepository` | None |
| Resale/Strony/Giełda (Plugin) | Separate plugin modules with their own repositories | None |
| Cloud Sync (V1+) | New `SyncModule` observing repository events | None |
| AI (V1+) | New `AIModule` reading reports | None |

**Rule**: Future modules may not bypass core application boundaries or directly manipulate core repositories. Extensions to core modules are allowed only through an explicitly designed future stage. Core module contracts are stable for MVP-1.

## 15. LEGACY REFERENCE DISPOSITION

### KEEP

- Pure calculator pattern (explicit inputs/outputs, no side effects)
- Repository pattern (entity-specific CRUD)
- Service orchestration layer
- Composition root concept
- StorageAdapter abstraction
- Testing per layer concept

### ADAPT

- SafeToSpendCalculator: remove `bills`, narrow output to `{ safeTotal, perDay }`
- BudgetProgressCalculator: align with archived Budget and monthly period
- GoalRequiredDepositCalculator: align with `ceil((target - current) / monthsLeft)` and `currentDate` input
- GoalEtaCalculator: align with G1.2 contract
- All application services: remove `window.*` globals, match G1.2 signatures
- All repositories: replace `remove()` with `archive()`, add `userId` filtering
- StorageAdapter: keep interface only, remove Firebase-specific notes
- Dependency matrix: rewrite for correct direction
- Entity schemas: align with G1.1
- Error handling: align with G1.2 error contracts

### DROP

- `window.*` global state
- `dbData` monolithic state
- Legacy storage keys
- Legacy metadata flags (`metadata.excluded`)
- Legacy money places (`konto`, `skarbonka`, `gielda`, `inne`)
- Transaction `type: 'transfer'`
- MVP-1 `tags`
- Hard-delete `remove()` at application/repository entity level
- Legacy sign semantics (negative amounts)
- Legacy service names (SourceNetService, MonthEarnStatsService, etc.)
- Legacy test conventions (window.* setup)
- V1+/Plugin modules mixed into MVP-1: TransferService, RecurringService, SavingsService, DebtService, NetWorthCalculator, DebtsCalculators, Resale/Gielda calculators
- `investment` account type in MVP-1
- Person/Debt/Loan entities for MVP-1
