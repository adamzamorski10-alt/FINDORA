# 0. NAJWAŻNIEJSZA ZMIANA W WERSJI 3.0

W wersji 3.0 zmieniamy główną strategię rozwoju Finory.

Dotychczas projekt był prowadzony jako stopniowa przebudowa starego, monolitycznego `index.html` w kierunku warstwowej architektury.

Ta praca przyniosła bardzo dużo wartości:

* poznaliśmy rzeczywistą architekturę aplikacji,
* znaleźliśmy problemy,
* wydzieliliśmy granice,
* wyciągnęliśmy logikę biznesową,
* zbudowaliśmy Storage Abstraction,
* przygotowaliśmy fundament migracji schematów,
* zbudowaliśmy podstawy State,
* uporządkowaliśmy ładowanie danych.

Jednak dalsze przepisywanie starego monolitu nie jest już najlepszą drogą.

Dlatego od wersji 3.0 obowiązuje:

> **NOWA FINORA BĘDZIE BUDOWANA GREENFIELD.**

Oznacza to, że:

```text
STARA FINORA
     ↓
Legacy Reference
     ↓
poznajemy:
- funkcje
- dane
- reguły biznesowe
- edge cases
- istniejące zachowanie
     ↓
NOWA FINORA
     ↓
projektowana od podstaw
na docelowej architekturze
```

Stara aplikacja odpowiada przede wszystkim na pytanie:

> **CO Finora robi?**

Nowa aplikacja odpowiada na pytanie:

> **JAK Finora powinna być zbudowana?**

Nie będziemy kopiować starej struktury tylko dlatego, że już istnieje.

Nie będziemy również bez końca usuwać każdego pozostałego śladu starej architektury, jeśli taka praca nie daje istotnej wartości nowemu systemowi.

# 1. CEL FINORA

Finora ma zostać prywatną, nowoczesną aplikacją do zarządzania finansami osobistymi.

Najważniejsza zasada architektoniczna:

> **Prywatne dane finansowe użytkownika mają przede wszystkim pozostawać na jego urządzeniu.**

Docelowo Finora ma być:

* local-first,
* możliwa do używania offline,
* prywatna,
* bezpieczna,
* modularna,
* testowalna,
* łatwa do dalszego rozwijania,
* odporna na utratę danych,
* gotowa na opcjonalny cloud,
* gotowa w przyszłości na opcjonalne AI,
* przygotowana do dalszego rozwoju przez AI Managera/Kilo Code.

Firebase nie będzie docelowo głównym miejscem przechowywania prywatnych danych finansowych.

Cloud może być wykorzystany opcjonalnie do:

* konta,
* zaszyfrowanego backupu,
* synchronizacji,
* odzyskiwania danych,
* innych funkcji, jeśli zostaną uznane za bezpieczne i potrzebne.

AI nie powinno automatycznie otrzymywać pełnej historii finansowej użytkownika.

Przyszła warstwa AI musi być projektowana zgodnie z zasadą:

> **Minimalizujemy dane przekazywane poza urządzenie.**

# 2. NAJWAŻNIEJSZE ZASADY PROJEKTU

Od wersji 3.0 obowiązują następujące zasady nadrzędne.

## 2.1 Greenfield zamiast dalszego przepisywania monolitu

Nowa Finora jest osobnym systemem.

Stary kod służy jako:

* dokumentacja zachowania,
* źródło reguł biznesowych,
* źródło danych i ich znaczenia,
* źródło edge cases,
* referencja funkcjonalna.

Nie służy jako:

* wzór architektury,
* wzór organizacji kodu,
* obowiązkowa struktura nowych modułów,
* powód do zachowywania złych rozwiązań.

---

## 2.2 Prywatność przed wygodą

Dane finansowe użytkownika powinny domyślnie pozostać lokalnie.

Cloud jest opcjonalny.

AI jest opcjonalne.

---

## 2.3 Poprawność danych przed szybkością

Finora jest aplikacją finansową.

Nie wolno poświęcać:

* poprawności obliczeń,
* integralności danych,
* bezpieczeństwa,
* możliwości odzyskania danych,
* izolacji użytkowników

tylko po to, żeby szybciej wdrożyć funkcję.

---

## 2.4 Prostota przed nadmierną abstrakcją

Nie tworzymy abstrakcji tylko dlatego, że dobrze wygląda na diagramie.

Każda warstwa i każdy moduł powinien mieć rzeczywistą odpowiedzialność.

Nie budujemy ogromnych „god modules”.

Nie tworzymy kilkudziesięciu repository bez potrzeby.

---

## 2.5 Plan jest adaptacyjny

Plan nie jest święty.

Jeżeli podczas pracy okaże się, że:

* można coś zrobić szybciej,
* można coś zrobić prościej,
* istnieje lepsza architektura,
* jakiś etap nie ma już sensu,
* jakaś praca jest tylko kosmetyczna,
* można połączyć małe etapy bez zwiększania ryzyka,

należy zmienić plan.

Głównym zadaniem architekta jest wybór najlepszej drogi, a nie ślepe trzymanie się starej kolejności.

# 4. ZASADA PRACY Z KILO CODE

Prompty dla AI kodującego muszą być projektowane pod tryb:

**FAST / EFFICIENT**

Każdy prompt powinien być możliwie krótki i mieć jasno ograniczony zakres.

Każdy prompt zaczyna się od:

```text
REASONING: LOW
```

lub:

```text
REASONING: MEDIUM
```

lub:

```text
REASONING: HIGH
```

### LOW

Domyślnie dla:

* prostych implementacji,
* małych zmian,
* testów,
* prostych migracji,
* prostych poprawek.

### MEDIUM

Dla:

* trudniejszej implementacji,
* debugowania,
* integracji kilku warstw,
* trudniejszych problemów logicznych.

### HIGH

Tylko dla:

* architektury,
* trudnych problemów bezpieczeństwa,
* końcowych hostile auditów,
* krytycznych decyzji projektowych.

Nie łączymy bez potrzeby:

```text
discovery
+
dużej implementacji
+
pełnej regresji
+
hostile auditu
```

w jednym promptcie.

Duże zadania dzielimy na logiczne etapy.

Naprawiono m.in.:

* context switching,

# 14. STAGE 1.6B.1 — LISTEN CONTRACT

Ujednolicono kontrakt listenera.

Callback otrzymuje:

**plain JavaScript value**

a nie Firebase `DataSnapshot`.

Zasady:

* initial callback jest asynchroniczny,
* kolejne zmiany są obsługiwane,
* unsubscribe jest dostępne,
* Firebase objects nie wychodzą poza adapter,
* `listen('')` nie jest ogólnym kontraktem,
* root listening jest osobną operacją `listenRoot()`.

Stage został zamknięty po korekcie testów i dokumentacji.

# 67. NACZELNA ZASADA ZARZĄDZANIA PROJEKTEM

Plan Finory ma być aktywnie zarządzany.

Nie obowiązuje zasada:

> „Skoro coś było w planie, musimy to zrobić.”

Obowiązuje:

> **„Robimy to, co najlepiej prowadzi Finorę do docelowego celu przy zachowaniu bezpieczeństwa, jakości i poprawności danych.”**

Jeżeli pojawi się lepsza droga:

**zmieniamy plan.**

Jeżeli coś okaże się niepotrzebne:

**usuwamy etap.**

Jeżeli coś można zrobić prościej:

**upraszczamy.**

Jeżeli coś można zrobić szybciej bez zwiększenia ryzyka:

**przyspieszamy.**

Jeżeli coś jest niebezpieczne:

**zatrzymujemy się.**

Jeżeli stare rozwiązanie jest dobre jako referencja, ale złe jako architektura:

**zachowujemy wiedzę, nie kopiujemy implementacji.**

To jest nadrzędna zasada prowadzenia całego projektu Finora.
